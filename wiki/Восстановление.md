# Восстановление

*Для кого: администратор сервера MFA Gate.*

Страница описывает, как вернуть базу MFA Gate из резервной копии: на том же сервере или на новом. Восстановление выполняет команда `mfagatectl restore`. Она проверяет копию и мастер-ключ, разворачивает копию в отдельную базу и только потом подменяет рабочую, поэтому неудачная попытка рабочую базу не портит.

## Зачем это нужно

Без восстановления потеря базы означает новую установку: заново подключать каталог, заводить RADIUS-клиенты и менять секреты на шлюзах, привязывать телефоны всем сотрудникам. С копией и мастер-ключом система возвращается в состояние на момент копии за несколько минут.

## Когда пригодится

- Данные в базе испорчены или удалены по ошибке.
- Сервер вышел из строя или вы переезжаете на другой.
- Нужно проверить, что резервные копии действительно восстанавливаются.

## Что потребуется

- Копия: каталог `<время>-<метка>` с файлами `db.dump`, `SHA256SUMS` и `manifest`.
- Мастер-ключ, с которым сделана копия. Без него `restore` откажется работать.
- Для нового сервера — сохранённый `deploy/.env`, а если настраивали push — `compose.override.yml` и файл учётных данных FCM.
- Решение, что данные после времени копии теряются: новые привязки телефонов, пользователи, история входов.

## Где найти

- Копии: `/opt/mfa-gate/deploy/backups/` и ваше внешнее хранилище.
- Команда: `sudo mfagatectl restore <каталог копии>`.

## Как это сделать

### Вариант 1. Тот же сервер

Подходит, если сервер и мастер-ключ на месте, а данные в базе нужно вернуть.

#### Шаг 1. Выберите копию

```bash
sudo ls -1t /opt/mfa-gate/deploy/backups | grep -v '^diag-' | head
```

**Что увидите:** каталоги вида `20261119T023000Z-daily`, новые сверху. Время в имени — UTC.

#### Шаг 2. Восстановите

```bash
sudo mfagatectl restore /opt/mfa-gate/deploy/backups/20261119T023000Z-daily
```

Команда по порядку:

1. сверяет контрольную сумму из `SHA256SUMS`;
2. сравнивает отпечаток текущего `master.key` с отпечатком в `manifest` и останавливается, если они не совпали;
3. останавливает `api`, `radius` и `worker` — с этого момента входы не проходят;
4. разворачивает копию во временную базу. Если это не удалось, рабочая база не тронута;
5. подменяет рабочую базу восстановленной; прежняя остаётся под именем `mfa_gate_prev` до следующего восстановления;
6. запускает сервисы и ждёт их готовности до 3 минут.

**Что увидите:**

```text
==> остановка api/radius/worker
==> восстановление базы из /opt/mfa-gate/deploy/backups/20261119T023000Z-daily
==> восстановлено; прежняя база сохранена как mfa_gate_prev
```

#### Шаг 3. Проверьте

```bash
sudo mfagatectl status && sudo mfagatectl diagnose
```

**Что увидите:** все сервисы `healthy`, в диагностике нет `FAIL`. Войдите в панель: пользователи, телефоны и настройки — на момент копии. Выполните пробный вход в VPN.

Телефоны, привязанные после времени копии, нужно привязать заново.

### Вариант 2. Новый сервер

Подходит, если прежний сервер потерян или вы переезжаете.

#### Шаг 1. Подготовьте сервер и адрес

Проверьте [Требования к серверу](Требования-к-серверу.md). Если у прежнего сервера было DNS-имя, направьте его на новый: тогда телефоны и шлюзы продолжат работать без перенастройки. Если меняется адрес, на шлюзах придётся сменить адрес RADIUS-сервера, а если меняется адрес из QR-кода (`MFA_GATE_DEVICE_URL` или `MFA_GATE_PUBLIC_URL`) — заново привязать телефоны.

#### Шаг 2. Получите ту же версию

Версию возьмите из строки `version=` в `manifest` копии.

```bash
sudo git clone https://github.com/calleograph/mfa-gate.git /opt/mfa-gate
sudo git -C /opt/mfa-gate checkout v0.3.2
```

Восстанавливайте копию в ту же версию, в которой она сделана: в более старую нельзя. Обновиться удобнее уже после восстановления: [Обновление](Обновление.md).

#### Шаг 3. Верните конфигурацию и мастер-ключ

Положите сохранённые файлы на новый сервер, например в `/root/restore/`, и разложите их по местам **до** установки:

```bash
cd /opt/mfa-gate/deploy
sudo install -m 600 /root/restore/.env .env
sudo install -d -m 700 data/secrets
sudo install -m 644 /root/restore/master.key data/secrets/master.key
sudo sha256sum data/secrets/master.key | cut -c1-16
```

**Что увидите:** отпечаток совпадает со строкой `master_key_sha256=` в `manifest` копии.

Если ключ сохранён строкой в менеджере паролей:

```bash
printf '%s\n' 'СТРОКА_КЛЮЧА' | sudo tee /opt/mfa-gate/deploy/data/secrets/master.key >/dev/null
sudo chmod 644 /opt/mfa-gate/deploy/data/secrets/master.key
```

Каталог `secrets` закрыт правами 700, а сам файл должен быть читаемым: его читает процесс внутри контейнера.

Сохранённый `.env` можно брать целиком: пароль базы из него подойдёт, потому что новая база создаётся при установке именно с этим паролем. Если адрес сервера меняется, исправьте `MFA_GATE_PUBLIC_URL` и `MFA_GATE_DEVICE_URL`. Если был push через FCM, верните `compose.override.yml` и файл учётных данных: [Настройка Push](Настройка-Push.md).

#### Шаг 4. Установите поверх сохранённой конфигурации

```bash
cd /opt/mfa-gate && sudo ./install.sh
```

**Что увидите:** на этапе «Конфигурация» — `найдена существующая конфигурация /opt/mfa-gate/deploy/.env — секреты и настройки сохраняются`; мастер-ключ заново не создаётся; в конце `Готово`. Версия берётся из `MFA_GATE_VERSION` в `.env`.

Установщик создаст в пустой базе временного администратора `admin`. После восстановления его не будет — это нормально.

#### Шаг 5. Восстановите копию

```bash
sudo mfagatectl restore /root/restore/20261119T023000Z-daily
```

Каталог копии может лежать где угодно. **Что увидите:** `восстановлено; прежняя база сохранена как mfa_gate_prev`.

#### Шаг 6. Проверьте и завершите

1. `sudo mfagatectl diagnose` — без `FAIL`.
2. Вход в панель под прежними администраторами, с прежними паролями и факторами.
3. Если адрес сервера изменился — адрес RADIUS-сервера на шлюзах, правила межсетевого экрана, reverse proxy и сертификат: [HTTPS через reverse proxy](HTTPS-через-reverse-proxy.md).
4. Пробный вход в VPN.
5. Включите расписание копий на новом сервере ([Резервное копирование](Резервное-копирование.md)) и удалите `/root/restore`.

### Удалить прежнюю базу

`mfa_gate_prev` занимает столько же места, сколько рабочая база, и удаляется сама при следующем восстановлении. Чтобы удалить её раньше, после проверки выполните:

```bash
cd /opt/mfa-gate/deploy
sudo docker compose --env-file .env -p mfa-gate exec -T postgres psql -U mfagate -d postgres -c 'DROP DATABASE mfa_gate_prev'
```

`mfa-gate` — значение `COMPOSE_PROJECT_NAME` из `.env`. Удалённую базу вернуть нельзя.

## Что получится

- Сервисы работают на восстановленной базе, диагностика без ошибок.
- Администраторы входят с прежними паролями и вторым фактором.
- Телефоны и TOTP сотрудников работают, если адрес из QR-кода не менялся.

Восстановление копии и подмена базы проверены в сквозных тестах установки; восстановление в составе отката — на тестовом сервере с настоящими данными.

## Если не получается

| Что видно | Почему | Что сделать |
|---|---|---|
| `… не похож на резервную копию MFA Gate` | в каталоге нет `db.dump` или `manifest` | укажите каталог копии, а не файл внутри него |
| `контрольная сумма копии не совпала` | копия повреждена | возьмите другую копию |
| `копия сделана с другим мастер-ключом: верните прежний data/secrets/master.key` | ключ на сервере не тот, с которым сделана копия | положите сохранённый ключ, выполните `sudo mfagatectl start` и повторите |
| `pg_restore не выполнен, рабочая база не тронута` | дамп не читается | возьмите другую копию; рабочая база осталась прежней |
| `после восстановления сервисы не стали healthy: ./mfagatectl logs` | версия кода не подходит к схеме копии | установите версию из `manifest` и повторите |
| Ошибка Docker о том, что `postgres` не запущен | контейнеры остановлены | `sudo mfagatectl start`, затем повторите |

### Если мастер-ключ утерян

Расшифровать секреты из копии невозможно, и `restore` откажется работать. Остаётся новая установка: подключить каталог, создать RADIUS-клиенты и сменить секреты на шлюзах, выдать сотрудникам TOTP и привязать телефоны заново.
