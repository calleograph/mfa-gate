# Справочник для проверки ИБ

*Для кого: служба информационной безопасности, архитектор, администратор, который готовит продукт к согласованию.*

Сведения о MFA Gate для внутренней проверки: какие данные обрабатываются и где хранятся, как защищены секреты, что уходит за пределы сервера, что журналируется, какие есть роли и ограничения и где проходят границы защиты. Отдельный раздел честно перечисляет, что ещё не проверено на настоящей инфраструктуре. Объяснение угроз и мер — [Безопасность и модель угроз](Безопасность-и-модель-угроз.md).

Сведения собраны по исходному коду и документам репозитория версии 0.3.1.

## 1. Состав системы

| Компонент | Что делает | Сеть |
| --- | --- | --- |
| `api` | Личный кабинет `/`, панель `/admin/`, REST API `/api/v1/`, Device API `/api/device/v1/` | HTTP 8080 в контейнере; на сервере — `MFA_GATE_HTTP_BIND:MFA_GATE_HTTP_PORT` |
| `radius` | RADIUS-сервер для VPN-шлюзов | UDP 1812 в контейнере; на сервере — `MFA_GATE_RADIUS_BIND:MFA_GATE_RADIUS_PORT` |
| `worker` | Доставка push, истечение запросов, удаление старых записей | Только исходящие соединения к службам push |
| `migrate` | Применяет миграции базы перед запуском остальных и завершается | — |
| `postgres` | PostgreSQL 16, единственное хранилище | Только внутренняя сеть контейнеров, наружу не публикуется |

Контейнеры приложения работают от непривилегированного пользователя (uid 10001), с файловой системой только для чтения, без Linux capabilities (`cap_drop: ALL`) и с `no-new-privileges`. Redis и другие хранилища не используются. Схема сети — [Сетевая схема и публикация](Сетевая-схема-и-публикация.md).

## 2. Обрабатываемые данные

| Категория | Состав | Где хранится | Защита при хранении |
| --- | --- | --- | --- |
| Учётные записи | Логин, отображаемое имя, почта, телефон, источник (локальный или каталог), objectGUID, группы каталога, статус, время последнего входа | PostgreSQL | Не шифруются |
| Доменные пароли | — | **Не хранятся**: передаются контроллеру домена при каждом входе | — |
| Пароли локальных пользователей и администраторов | — | PostgreSQL | argon2id |
| Секреты TOTP | Секрет каждого приложения-аутентификатора | PostgreSQL | AES-256-GCM, мастер-ключ |
| Общие секреты RADIUS-клиентов | — | PostgreSQL | AES-256-GCM, мастер-ключ |
| Пароли сервисных учётных записей каталога | — | PostgreSQL | AES-256-GCM, мастер-ключ |
| Push-токены телефонов | Адрес доставки FCM, HMS или UnifiedPush | PostgreSQL | AES-256-GCM, мастер-ключ |
| Открытые ключи телефонов | ECDSA P-256 | PostgreSQL | Не требуется: ключ открытый |
| Секреты устройств, ключи API, токены привязки, токены сессий, аварийные коды | — | PostgreSQL | Только SHA-256; запись ищется по хешу предъявленного значения |
| Резервные коды личного кабинета | — | PostgreSQL | HMAC-SHA256 на ключе, производном от мастер-ключа, с привязкой к пользователю; коды из 0.3.0 (SHA-256) тоже принимаются |
| История входов | Логин, ресурс, RADIUS-клиент, адрес источника (Calling-Station-Id), канал, способ, итог, причина, устройство, время | PostgreSQL, 180 дней | Не шифруется |
| Журнал аудита | Событие, кто, адрес, объект, итог, подробности без секретов | PostgreSQL, 365 дней | Не шифруется; записи не подписываются |
| Резервные копии | Дамп базы `pg_dump` | `deploy/backups/`, каталог 700 | Секреты внутри остаются зашифрованными; мастер-ключ в копию не входит |
| Журналы контейнеров | Технические сообщения служб | Docker, до 5 файлов по 10 МБ на службу | Секреты не пишутся |

На телефоне закрытый ключ создаётся в Android Keystore и не извлекается из него. Резервные коды — 10 одноразовых кодов, показываются сотруднику один раз и действуют только для входа в личный кабинет, не для VPN.

## 3. Мастер-ключ и шифрование секретов

| Вопрос | Ответ |
| --- | --- |
| Что это | 32 случайных байта в base64, файл `deploy/data/secrets/master.key` |
| Как создаётся | `mfagatectl install` при первой установке (`openssl rand`), повторно не перезаписывается |
| Как попадает в приложение | Docker secret: файл монтируется в контейнеры как `/run/secrets/master_key`. В базе, в `.env` и в Git ключа нет |
| Права | Каталог `secrets` — 700 (root), файл — 644, чтобы его прочитал процесс контейнера |
| Алгоритм | AES-256-GCM, случайный nonce 96 бит, версия формата. Шифртекст привязан к записи через дополнительные данные (AAD: `totp:<id>`, `radius:<id>`, `ldap:<id>`, `push:<id>`), поэтому его нельзя перенести в другую запись |
| Резервные копии | Ключ в копию не входит. В манифесте копии — первые 16 символов SHA-256 ключа; `restore` откажет, если ключ другой |
| Потеря ключа | Секреты TOTP, RADIUS, каталогов и push-токены не расшифровать: придётся заново выпустить факторы и ввести секреты |
| Смена ключа | **Встроенной смены нет.** Формат версионирован, но команды перешифрования нет. HSM и внешние хранилища секретов не поддерживаются |

## 4. Подтверждение входа на телефоне

| Шаг | Как защищено |
| --- | --- |
| Привязка | Одноразовый токен 256 бит в QR-коде, на сервере только хеш. Срок — 24 часа из панели (`MFA_GATE_ENROLLMENT_TTL_HOURS`), 15 минут из личного кабинета. Перед привязкой телефон показывает адрес сервера и учётную запись. На адрес `http://` приложение привязывается только после явного подтверждения риска |
| Ключ | При привязке телефон создаёт ключ ECDSA P-256 в Android Keystore. Каждая подпись требует биометрии или PIN-кода телефона |
| Запрос | На каждый вход сервер создаёт случайный challenge 32 байта |
| Решение | Телефон подписывает строку `mfa-gate-decision-v1`, идентификатор запроса, идентификатор устройства, challenge и решение `approve` или `deny`. Решение входит в подпись, поэтому «отклонить» нельзя превратить в «подтвердить» |
| Проверка | Сервер принимает подпись только от устройства владельца запроса и только пока запрос ожидает ответа и не истёк. Статус меняется одной атомарной операцией: второй ответ получает `409`, ответ после таймаута ничего не открывает |
| Служебные запросы | Список запросов и обновление push-токена — по секрету устройства, без биометрии. Подтвердить вход этим секретом нельзя |
| Отзыв | Администратор или сотрудник отзывает устройство; отозванное устройство получает `401` на любой запрос |

Протокол целиком — [docs/protocol/device-api.md](https://github.com/calleograph/mfa-gate/blob/main/docs/protocol/device-api.md).

## 5. RADIUS

| Мера | Подробности |
| --- | --- |
| Только PAP | Пароль защищён общим секретом по RFC 2865. Остальные атрибуты передаются открыто, поэтому между площадками RADIUS пускают только внутри IPsec или WireGuard |
| Известные клиенты | Клиент определяется по адресу источника. Пакет с неизвестного адреса молча отбрасывается |
| Message-Authenticator | Обязателен во всех входящих пакетах (`MFA_GATE_RADIUS_REQUIRE_MESSAGE_AUTHENTICATOR=true`) и всегда стоит первым атрибутом в ответах. Это защита от атаки BlastRADIUS (подделка ответа). Неверный атрибут — отброс пакета и событие `radius.bad_authenticator` не чаще раза в минуту на клиента |
| Повторы шлюза | Повторный пакет не создаёт второй запрос и получает тот же ответ (RFC 5080). Новая попытка присоединяется к открытой только при совпадении пользователя, ресурса, Calling-Station-Id, клиента и NAS: чужая попытка не может воспользоваться push жертвы |
| Режим «Сам шлюз» | Если шлюз сам проверяет доменный пароль, MFA Gate доверяет этому только для конкретного RADIUS-клиента; глобального пропуска первого фактора нет. Такому клиенту нужны свой длинный секрет и фильтрация UDP 1812 по адресу ([Шлюзы с собственной проверкой пароля](Шлюзы-с-собственной-проверкой-пароля.md)) |
| Не реализовано | RadSec (RADIUS по TLS), RADIUS Accounting, атрибуты ответа |

## 6. Что уходит за пределы сервера

| Направление | Когда | Какие данные | Как отключить |
| --- | --- | --- | --- |
| Контроллеры домена, LDAPS 636 или STARTTLS 389 | Вход сотрудника, поиск в каталоге, диагностика | Логин, пароль при проверке, запросы атрибутов и групп | Не подключать каталог. Режим без шифрования возможен, но диагностика предупреждает о нём |
| Firebase Cloud Messaging (`oauth2.googleapis.com`, `fcm.googleapis.com`) | Вход с подтверждением на телефоне, если FCM настроен | Только сигнал: тип, идентификатор запроса, идентификатор устройства, версия. Логина, ресурса, адреса и времени в нём нет | Не задавать `MFA_GATE_PUSH_FCM_CREDENTIALS_FILE` |
| Huawei Push Kit | То же, если заданы переменные HMS (экспериментально) | То же | Не задавать переменные HMS |
| Распределитель UnifiedPush | То же, если хост в списке `MFA_GATE_PUSH_UNIFIEDPUSH_HOSTS` (экспериментально) | То же; только `https://` и только хосты из списка | Оставить список пустым |
| GitHub API | Только по команде `mfagatectl check-update` на сервере | Запрос последнего выпуска, без данных установки | Не выполнять команду |
| GitHub, реестр образов, репозитории пакетов, `get.docker.com` | Только `install.sh`, `mfagatectl install` и `update` | Загрузка образов и пакетов | Ставить из локального реестра |

Подробности входа телефон получает сам, по HTTPS с вашего сервера: логин, ресурс, адрес источника, клиент, время. Геолокация адреса не определяется. Без настроенной службы push приложение получает запросы только по прямому соединению с сервером. При чтении кода других исходящих соединений и телеметрии не найдено.

## 7. Публикация наружу

| Что | Где доступно |
| --- | --- |
| Device API (`/api/device/`) | Из Интернета по внешнему имени `MFA_GATE_DEVICE_URL`, например `https://auth.example.org`: телефон подтверждает вход до того, как поднят VPN |
| Личный кабинет, панель, REST API | Только внутренняя сеть, имя `MFA_GATE_PUBLIC_URL`, например `https://mfa.example.org` |
| RADIUS | Только адреса VPN-шлюзов, ограничение межсетевым экраном |
| PostgreSQL | Не публикуется |

Защита выстроена в два рубежа. Reverse proxy публикует внешнее имя только с префиксом `/api/device/`. Если прокси настроен с ошибкой, сам сервер на внешнем имени ответит `404` на всё, кроме `/api/device/` и `/health/`. Второй рубеж работает, только когда прокси передаёт исходный заголовок `Host`, и не защищает внутреннее имя: его закрывают правила прокси по адресам источника. Готовые конфигурации — `deploy/proxy/nginx.conf`, `deploy/proxy/Caddyfile`, экран **Адреса и публикация**.

## 8. Вход, сессии и ограничения частоты

| Механизм | Значение |
| --- | --- |
| Временная блокировка учётной записи | После 8 ошибок пароля или кода на 15 минут. Счётчик общий для форм `user`, `DOMAIN\user` и UPN |
| Попытки входа в панель и кабинет | 20 в минуту с одного адреса; счётчик в PostgreSQL, общий для всех экземпляров `api` |
| Привязка телефонов | 30 в минуту с одного адреса |
| Ответ при ошибке первого фактора | Один и тот же текст для неверного пароля, неизвестного логина, блокировки и отключённой записи. Точная причина — только в истории входов и журнале |
| Защита TOTP | RFC 6238: 6 цифр, шаг 30 с, допускается соседний шаг (расхождение часов до ±30 с); принятый код повторно не принимается |
| Срок ответа на push | 45 с (`MFA_GATE_PUSH_TIMEOUT`), затем отказ `push_expired` |
| Сессия панели | До второго фактора 10 минут и только шаги входа; после — 30 минут с продлением. Второй фактор обязателен для всех ролей |
| Сессия кабинета | До второго фактора 15 минут; после — 30 минут с продлением. Сессия кабинета не открывает панель |
| Cookie | `HttpOnly`, `SameSite=Strict`, `Secure` при HTTPS |
| CSRF | Заголовок `X-CSRF-Token` у всех изменяющих запросов панели |
| Заголовки | CSP `script-src 'self'` без встроенных скриптов, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` |

## 9. Самостоятельная настройка сотрудниками

Первую настройку способа входа сотрудник неизбежно проходит по одному паролю. Чтобы укравший пароль не привязал свой телефон, действуют все меры сразу:

- у сотрудника **никогда** не было способа входа (отметка не снимается при удалении способов) или администратор нажал **Разрешить повторную настройку** — разрешение действует 24 часа и гаснет после настройки;
- адрес входит в `MFA_GATE_PORTAL_ENROLL_NETWORKS` (по умолчанию частные сети);
- сотрудник входит в группу из `MFA_GATE_PORTAL_ENROLL_GROUPS`, если список задан;
- новые способы после первого добавляются только в сессии, подтверждённой вторым фактором; последний способ удалить нельзя;
- каждая настройка и каждый отказ пишутся в журнал аудита.

Остаточный риск: злоумышленник с паролем сотрудника, который ещё ни разу не настраивал способ входа, из разрешённой сети. Его снижают ранней рассылкой и узкими сетями и группами ([Первичная настройка сотрудниками](Первичная-настройка-сотрудниками.md)).

## 10. Роли и учётные записи

| Учётная запись | Права | Как защищена |
| --- | --- | --- |
| Главный администратор, администратор, оператор, аудитор | По ролям ([Справочник: роли и права](Справочник-роли-и-права.md)) | Пароль и обязательный второй фактор |
| Ключи REST API | Только выданные права, без управления администраторами; можно привязать к ресурсу и ограничить сетями | Секрет показывается один раз, хранится как хеш |
| Сервисная учётная запись каталога | Достаточно права чтения каталога | Пароль зашифрован мастер-ключом; вход возможен и без неё |
| root на сервере | Всё, включая аварийный код и новых администраторов | Ограничивается средствами ОС; каждое действие из консоли пишется в журнал |
| Учётная запись PostgreSQL `mfagate` | Только своя база | Пароль в `.env` (600), база не публикуется |

## 11. Журналы

Журнал аудита ведёт 51 вид событий: входы в панель и кабинет, решения по входам, изменения настроек, выпуск кодов и ключей, аварийный доступ. Значения полей с признаками секрета (`password`, `secret`, `token`, `code`, `otp`, `signature`, `key`, `challenge`) всегда маскируются. Архив `mfagatectl diagnose` не создаётся, если в нём найдётся пароль базы или мастер-ключ. Выгрузка — CSV из панели или через REST API. Встроенной отправки в SIEM по syslog нет: журнал забирают через API (`GET /api/v1/audit`, право `audit:read`). Полный перечень — [Справочник: журнал аудита](Справочник-журнал-аудита.md).

## 12. Поведение при сбоях

| Сбой | Поведение |
| --- | --- |
| Каталог недоступен | Отказ (`directory_unavailable`) |
| Ошибка вычисления вложенных групп AD | Отказ, без отката к прямым группам |
| Нет способа входа, push не доставлен, нет ответа | Отказ (`no_factor`, `push_expired`) |
| База данных недоступна | RADIUS молчит или отвечает отказом, `api` — `503`; после возврата базы работа продолжается без перезапуска |
| Пропуск без второго фактора | Только явной политикой с действием **Пропустить без MFA** (`allow`) или вариантом **Пропустить по паролю** (`on_unavailable=allow`) для указанных ресурсов и групп. Каждый такой вход пишется в журнал (`auth.accept`): по варианту **Пропустить по паролю** — с важностью «Внимание», по действию **Пропустить без MFA** — «Обычное». Создание или изменение такой политики записывается с важностью «Внимание». На вход администраторов в панель политики не действуют |
| Аварийный доступ администратора | Только одноразовым кодом из консоли сервера, 15 минут, событие «Критичное» |

## 13. Чего нет

- Подтверждения вводом числа (number matching) и ограничения частоты push на одного пользователя: от «усталости от push» защищают только первый фактор перед push, один push на попытку, блокировка и кнопка **Отклонить**.
- Счётчика ошибок по адресу шлюза или клиента: перебором можно временно заблокировать чужую учётную запись.
- Смены мастер-ключа, HSM, подписи или цепочки хешей в журнале аудита.
- RadSec, RADIUS Accounting, атрибутов ответа, WebAuthn.
- Отпечатка ключа сервера в QR-коде привязки: подлинность сервера при привязке обеспечивает только TLS.

Планы — [Планы развития](Планы-развития.md).

## 14. Что не проверено

На настоящей инфраструктуре проверены установка на чистый Ubuntu Server, обновление и откат, личный кабинет и вход по RADIUS с настоящим каталогом OpenLDAP и подтверждением (телефон имитировался программой). **Не проверены:**

| Что | Чем заменено |
| --- | --- |
| Настоящие VPN-шлюзы сторонних производителей | RADIUS проверен собственным клиентом по сети и сквозными тестами; режим «Сам шлюз» — имитацией пакетов по документации производителя |
| Настоящий Active Directory | OpenLDAP с TLS; правила вложенных групп AD — юнит-тестами |
| Приложение на реальном телефоне: Keystore и биометрия, камера, работа в фоне | Подпись и протокол — имитацией телефона; приложение — JVM-тестами и сборкой |
| Доставка через FCM, HMS, UnifiedPush | Нет учётных данных; проверен только прямой опрос сервера |
