# Подключение VPN

*Для кого: сетевой администратор и администратор MFA Gate, который подключает VPN-шлюз.*

Страница описывает общий порядок подключения любого VPN-шлюза к MFA Gate по RADIUS и требования, без которых вход с подтверждением не заработает. В конце — таблица совместимости с распространёнными шлюзами. Когда всё настроено, сотрудник вводит логин и пароль в VPN-клиенте, подтверждает вход на телефоне или вводит код, и туннель поднимается.

## Зачем это нужно

VPN-шлюз умеет спрашивать внешний RADIUS-сервер, пускать ли пользователя. MFA Gate и есть такой сервер: он проверяет пароль, затем второй фактор и отвечает шлюзу «пустить» или «не пускать». Шлюз ничего не знает о телефонах и кодах, а MFA Gate не участвует в самом туннеле.

## Когда пригодится

- Вы подключаете первый VPN-шлюз после установки MFA Gate.
- Добавляете второй шлюз: другую площадку, резервный узел, отдельный VPN для подрядчиков.
- Переводите шлюз с проверки пароля в каталоге на проверку с подтверждением.

Если приложение само принимает логин и пароль и умеет делать HTTP-запросы, RADIUS не нужен: [Интеграция по REST API](Интеграция-по-REST-API.md). Для OpenVPN есть готовый скрипт: [Подключение OpenVPN](Подключение-OpenVPN.md).

## Что потребуется

- MFA Gate установлен, каталог подключён, у тестового сотрудника `ivanov` есть второй фактор: телефон или TOTP.
- Права в панели на разделы **Ресурсы** и **RADIUS-клиенты**: роль **Главный администратор** или **Администратор**.
- Доступ к настройкам VPN-шлюза.
- Адрес, с которого RADIUS-пакеты шлюза приходят на сервер MFA Gate (после NAT), например `198.51.100.1`.
- Внешний адрес Device API, если сотрудники будут входить из дома: [Сетевая схема и публикация](Сетевая-схема-и-публикация.md).

## Требования к шлюзу

| Что | Требование | Почему |
|---|---|---|
| Протокол | RADIUS, UDP 1812 (или ваш `MFA_GATE_RADIUS_PORT`) | RadSec не реализован |
| Метод передачи пароля | **PAP** | MFA Gate сам проверяет пароль в каталоге, поэтому должен получить его. На CHAP и MS-CHAPv2 отвечает отказом «Поддерживается только PAP» |
| Message-Authenticator | шлюз должен его отправлять | без него пакет отбрасывается: защита от атаки BlastRADIUS. В **Журнале** появляется событие «Неверный RADIUS-аутентификатор» |
| Таймаут ожидания ответа | **не меньше 60 с** | MFA Gate держит запрос, пока сотрудник отвечает на телефоне, до 45 с. Многие шлюзы по умолчанию ждут несколько секунд |
| Повторы | 1–3 | повтор не создаёт второй push |
| Accounting | выключен | RADIUS Accounting не реализован |
| Calling-Station-Id | желательно передавать | этот адрес сотрудник видит в запросе на телефоне; без него повторный запрос шлюза не присоединяется к открытому push |
| Access-Challenge | желательно поддерживать | нужен для ввода кода TOTP, если у сотрудника нет телефона |

Ответ Access-Accept не содержит атрибутов Class, Filter-Id и других: назначать группы или пулы адресов по ответу RADIUS нельзя. Эта функция есть в [Планах развития](Планы-развития.md).

## Кто проверяет доменный пароль

У каждого RADIUS-клиента есть поле **Кто проверяет доменный пароль** с двумя вариантами.

| Вариант | Что присылает шлюз | Что делает MFA Gate | Когда выбирать |
|---|---|---|---|
| **MFA Gate** (по умолчанию) | логин и пароль по PAP | проверяет пароль в каталоге или у локальной учётной записи, затем второй фактор | почти всегда |
| **Сам шлюз** | логин с пустым паролем или логин и одноразовый код | пароль не проверяет, спрашивает только второй фактор | шлюз сам проверяет доменный пароль до запроса в MFA Gate |

Вариант **Сам шлюз** снимает проверку пароля с MFA Gate для этого клиента. Если поставить его шлюзу, который пароль не проверяет, любой, кто знает логин, сможет отправить сотруднику push. Подробно: [Шлюзы с собственной проверкой пароля](Шлюзы-с-собственной-проверкой-пароля.md).

## Где найти

- RADIUS-клиент: **Панель → Интеграции → RADIUS-клиенты → Добавить клиент**.
- Ресурс, если нужен заранее: **Панель → Интеграции → Ресурсы → Добавить ресурс**.
- Проверка: **Панель → Контроль → История входов** и **Панель → Контроль → Журнал**.

## Как это сделать

1. **Добавьте RADIUS-клиент.** **Панель → Интеграции → RADIUS-клиенты → Добавить клиент**:

   | Поле | Значение |
   |---|---|
   | **Название** | `Шлюз VPN в офисе` |
   | **Ресурс** | **Создать автоматически**. Ресурс — то, что защищает MFA Gate; на него ссылаются политики. Если один ресурс нужен нескольким шлюзам, создайте его заранее в **Ресурсах** и выберите здесь |
   | **Адрес шлюза** | `198.51.100.1` — адрес, с которого пакеты приходят на сервер |
   | **NAS-Identifier** | пусто; если заполнить, значение должно совпадать с атрибутом в запросе шлюза |
   | **Кто проверяет доменный пароль** | **MFA Gate** |
   | **Общий секрет** | оставьте пустым: MFA Gate сгенерирует надёжный секрет |
   | **Клиент включён** | включено |

   Нажмите **Создать**.

   **Что увидите:** окно «Секрет RADIUS-клиента «Шлюз VPN в офисе»» с полем **Общий секрет**. Скопируйте секрет сразу: он показывается один раз. Новый клиент начинает принимать запросы не позже чем через 15 с, перезапуск не нужен. В **Ресурсах** появится ресурс VPN `Шлюз VPN в офисе`.

2. **Проверьте политику.** По умолчанию для ресурса требуется второй фактор способами push и TOTP. Если нужны другие правила для групп, настройте их: [Политики доступа](Политики-доступа.md).

3. **Настройте шлюз.** Добавьте RADIUS-сервер аутентификации:

   | Параметр шлюза | Значение |
   |---|---|
   | Адрес сервера | `192.0.2.10` |
   | Порт | `1812` |
   | Общий секрет | секрет из шага 1 |
   | Метод | PAP |
   | Таймаут | 60 с |
   | Повторы | 1–3 |
   | Accounting | выключен |

   Назначьте этот сервер группе или профилю VPN, через который входят сотрудники.

4. **Откройте сеть.** UDP 1812 на сервер MFA Gate — только с адреса шлюза. Если шлюз и MFA Gate на разных площадках, RADIUS идёт внутри IPsec или WireGuard: RADIUS шифрует только пароль, остальные атрибуты видны. Правила: [Сетевая схема и публикация](Сетевая-схема-и-публикация.md).

5. **Проверьте вход** по списку ниже.

## Что получится

Сотрудник вводит логин и пароль в VPN-клиенте. Через несколько секунд на телефон приходит запрос с названием ресурса и адресом. Сотрудник нажимает «Подтвердить», подтверждает биометрией — туннель поднимается. Если телефона нет, а TOTP есть, VPN-клиент показывает окно «Введите одноразовый код». Как это выглядит по шагам: [Архитектура: последовательности входа](Архитектура-Последовательности-входа.md).

## Как проверить

1. Верный пароль → на телефон приходит запрос → «Подтвердить» → VPN подключается.
2. «Отклонить» на телефоне → отказ приходит сразу, в **Истории входов** причина «Push отклонён».
3. Неверный пароль → отказ сразу, push не приходит, причина «Каталог не принял пароль».
4. Нет ответа на телефоне → отказ через 45 с, а не раньше по таймауту шлюза. Причина «Нет ответа на push».
5. Подтверждение на 30–40-й секунде проходит.
6. Повторы шлюза не дают второго уведомления.
7. Сотрудник только с TOTP: VPN-клиент показывает запрос кода, кириллица читается, код принимается, повтор того же кода отклоняется.
8. В **Истории входов** канал «RADIUS», ресурс и клиент `Шлюз VPN в офисе`, адрес сотрудника.
9. В **Журнале** нет событий «Неверный RADIUS-аутентификатор».
10. У RADIUS-клиента в столбце **Последний запрос** стоит свежее время.

## Совместимость со шлюзами

Протокол RADIUS MFA Gate покрыт сквозными тестами собственным RADIUS-клиентом. **На настоящих шлюзах настройки не проверялись.** Таблица собрана по описанию протокола и общедоступной документации; перед внедрением проверьте свой шлюз по списку выше. Если проверили, пришлите поправки: [Участие в разработке](Участие-в-разработке.md).

| Шлюз | Как подключается | PAP | Запрос кода (Access-Challenge) | Что учесть |
|---|---|---|---|---|
| OpenVPN 2.5+ со скриптом MFA Gate | REST API, без RADIUS | — | через `static-challenge` в клиенте | рекомендуемый способ для OpenVPN: [Подключение OpenVPN](Подключение-OpenVPN.md) |
| OpenVPN с модулем PAM RADIUS | RADIUS | да | зависит от версий плагина и клиента | модуль старше 3.0 может не отправлять Message-Authenticator |
| Межсетевой экран или VPN-концентратор с RADIUS PAP | RADIUS | да | у многих моделей есть, сверьтесь с документацией шлюза | таймаут удалённой аутентификации по умолчанию часто несколько секунд — поднимите до 60 с; Accounting не включайте |
| Сервер OpenVPN, встроенный в межсетевой экран | RADIUS | да | обычно нет: работает только push | таймаут аутентификации — 60 с |
| Windows NPS и RRAS | RADIUS через NPS в режиме пересылки | только для клиентов, которые передают пароль по PAP | нет данных | клиенты Windows VPN обычно используют MS-CHAPv2 или EAP, из них пароль не извлечь — такой вход работать не будет. RADIUS-клиентом в MFA Gate заводится адрес сервера NPS |
| Шлюз, который сам проверяет доменный пароль | RADIUS, вариант **Сам шлюз** | да | в режиме «только логин» | [Шлюзы с собственной проверкой пароля](Шлюзы-с-собственной-проверкой-пароля.md) |
| Шлюз, у которого таймаут нельзя поднять выше 10 с | RADIUS | да | часто нет | push не успеет. Варианты: уменьшить `MFA_GATE_PUSH_TIMEOUT` и попросить сотрудников держать приложение открытым либо выдать TOTP, если шлюз поддерживает Access-Challenge |

Вариант **Сам шлюз** не поможет шлюзу, который пересылает MS-CHAPv2: пароль из MS-CHAPv2 не извлечь, а пустого пароля или кода по PAP такой шлюз не присылает.

## Если не получается

| Что видно | Почему | Что сделать |
|---|---|---|
| Шлюз пишет «сервер не отвечает», **Последний запрос** у клиента пустой | пакеты не доходят или приходят с другого адреса | проверьте маршрут и правило UDP 1812; укажите адрес после NAT; посмотрите журнал контейнера `radius` |
| В **Журнале** «Неверный RADIUS-аутентификатор» | неверный общий секрет или шлюз не отправляет Message-Authenticator | сверьте секрет, при необходимости **Сменить секрет**; включите Message-Authenticator на шлюзе |
| VPN-клиент показывает «Поддерживается только PAP» | шлюз использует CHAP или MS-CHAPv2 | включите PAP |
| Подтверждение на телефоне прошло, VPN-клиент уже показал ошибку | таймаут шлюза меньше времени ответа | поднимите таймаут до 60 с |
| На один вход приходит два уведомления | шлюз не передаёт Calling-Station-Id и шлёт новые запросы вместо повторов | включите передачу Calling-Station-Id |
| Запрос кода не появляется, сотрудник только с TOTP получает отказ | шлюз не поддерживает Access-Challenge | привяжите телефон или используйте шлюз с поддержкой Access-Challenge |
| Отказ с причиной «Нет второго фактора» | у сотрудника нет телефона и TOTP или политика не разрешает доступный способ | [Управление пользователями](Управление-пользователями.md), [Политики доступа](Политики-доступа.md) |

Разбор по симптомам: [Решение проблем входа в VPN](Решение-проблем-входа-в-VPN.md).
