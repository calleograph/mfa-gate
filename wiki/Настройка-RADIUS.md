# Настройка RADIUS

Цепочка: **ресурс** (куда входят, например «VPN офис») → **RADIUS-клиент** (шлюз, который спрашивает MFA Gate) → **настройки на шлюзе**.

Справочник по правилам протокола (PAP, Access-Challenge, повторы, атрибуты): [docs/integrations.md](https://github.com/calleograph/mfa-gate/blob/main/docs/integrations.md). Настройка конкретных шлюзов: [Подключение VPN](Подключение-VPN.md).

В примерах: сервер MFA Gate `192.0.2.10`, VPN-шлюз `198.51.100.1`.

## Шаг 1. Ресурс

«Ресурсы» → «Добавить ресурс»:

- Название: `VPN офис`;
- Тип: VPN («Шлюз проверяет вход по RADIUS»);
- Ресурс включён: да.

**Ожидаемый результат:** «Ресурс создан», ресурс в списке.

Ресурс нужен, чтобы политики и история входов различали, куда именно входят. Выключенный ресурс отклоняет все входы с причиной `resource_disabled`.

## Шаг 2. RADIUS-клиент

«RADIUS-клиенты» → «Добавить клиент»:

| Поле | Значение |
|---|---|
| Название | `Шлюз VPN в офисе` |
| Ресурс | `VPN офис` |
| Адрес шлюза | `198.51.100.1` — адрес, **с которого пакеты приходят на MFA Gate**. Если между шлюзом и MFA Gate есть NAT, укажите адрес после NAT. Можно указать сеть: `198.51.100.0/28` |
| NAS-Identifier | необязательно. Если задан, пакеты с другим значением отбрасываются |
| Первый фактор | `mfa_gate` (по умолчанию) — шлюз пересылает пароль, MFA Gate проверяет его в AD или локально. `gateway` — только если шлюз сам проверяет доменный пароль и присылает пустой пароль или код TOTP (например, [Ideco](Подключение-Ideco.md)) |
| Общий секрет | оставьте пустым — MFA Gate сгенерирует надёжный секрет. Свой — от 16 символов |
| Клиент включён | да |

Нажмите «Создать».

**Ожидаемый результат:** окно «Секрет RADIUS-клиента «Шлюз VPN в офисе»» с общим секретом.

**Секрет показывается один раз.** Скопируйте его в менеджер паролей и только потом нажмите «Секрет сохранён, закрыть». На сервере он хранится зашифрованным и больше не показывается. Если секрет потерян — в меню клиента «Сменить секрет», затем обновите его на шлюзе.

Изменения применяются в течение 15 секунд, перезапуск не нужен.

**Как проверить:** клиент в списке, колонка «Последний запрос» пока пуста. После первого пакета от шлюза там появится время.

## Шаг 3. Настройки на шлюзе

Общие для всех шлюзов значения:

| Параметр шлюза | Значение |
|---|---|
| Адрес RADIUS-сервера | `192.0.2.10` |
| Порт аутентификации | `1812` (или ваш `MFA_GATE_RADIUS_PORT`) |
| Общий секрет | секрет из шага 2 |
| Метод проверки пароля | **PAP**. CHAP и MS-CHAPv2 не поддерживаются: в режиме `mfa_gate` MFA Gate сам проверяет пароль и должен его получить |
| Message-Authenticator | **включён**. Пакеты без него отбрасываются (защита от BlastRADIUS) |
| Таймаут ожидания ответа | **не меньше 60 секунд** |
| Число повторов | 1–2 |
| RADIUS Accounting (порт 1813) | **выключить** — не поддерживается |
| Calling-Station-Id | передавать (IP сотрудника будет виден в запросе на телефоне) |

### Почему таймаут не меньше 60 секунд

При push MFA Gate держит запрос открытым, пока сотрудник не ответит на телефоне, — до `MFA_GATE_PUSH_TIMEOUT` (по умолчанию 45 с). Если шлюз ждёт меньше, сотрудник подтверждает вход на телефоне, а VPN-клиент уже показал ошибку. Правило: таймаут шлюза ≥ `MFA_GATE_PUSH_TIMEOUT` + 15 с.

Если шлюз не позволяет поставить больше, например, 30 секунд, уменьшите время на ответ в `/opt/mfa-gate/deploy/.env`:

```bash
sudo sed -i 's/^MFA_GATE_PUSH_TIMEOUT=.*/MFA_GATE_PUSH_TIMEOUT=20/' /opt/mfa-gate/deploy/.env && sudo mfagatectl start
```

**Как проверить:** `sudo grep PUSH_TIMEOUT /opt/mfa-gate/deploy/.env` → `MFA_GATE_PUSH_TIMEOUT=20`.

Повторы шлюза безопасны: повтор того же пакета не создаёт второй вход и не шлёт второй push.

## Шаг 4. Доступ к порту RADIUS

UDP 1812 должен быть доступен **только адресам шлюзов**. Пакеты от незарегистрированных адресов MFA Gate и так молча отбрасывает, но лишний открытый порт показывает сервис снаружи.

Важно: порты, опубликованные Docker, **обходят правила `ufw`**. `ufw allow`/`ufw deny` на 1812 не действуют. Фильтровать нужно в цепочке `DOCKER-USER`:

```bash
sudo iptables -I DOCKER-USER -p udp -m conntrack --ctorigdstport 1812 --ctdir ORIGINAL -j DROP
sudo iptables -I DOCKER-USER -p udp -m conntrack --ctorigdstport 1812 --ctdir ORIGINAL -s 198.51.100.1 -j ACCEPT
sudo apt-get install -y iptables-persistent && sudo netfilter-persistent save
```

Вторая команда вставляется выше первой, поэтому порядок такой: сначала разрешение шлюзу, потом запрет остальным. Для каждого шлюза добавьте своё правило `ACCEPT`.

**Как проверить:** `sudo iptables -L DOCKER-USER -n --line-numbers` — строка `ACCEPT … 198.51.100.1` выше строки `DROP`.

Правила зависят от настроек Docker и бэкенда (iptables или nftables) — проверьте их на своём хосте. Если между шлюзом и сервером есть внешний межсетевой экран (облачная группа безопасности, аппаратный экран), откройте UDP 1812 и там.

## Шаг 5. Проверка с самого сервера: `mfagatectl radius-test`

Команда отправляет тестовый Access-Request из контейнера `api` в `radius` по внутренней сети Docker. Чтобы пакет не был отброшен, на время проверки нужен RADIUS-клиент с адресом этой сети.

1. Узнайте подсеть:

   ```bash
   sudo docker network inspect mfa-gate_backend -f '{{(index .IPAM.Config 0).Subnet}}'
   ```

   **Ожидаемый результат:** сеть вида `172.18.0.0/16`. Имя сети — `<COMPOSE_PROJECT_NAME>_backend`; если вы меняли имя экземпляра, подставьте своё.

2. Добавьте RADIUS-клиент «Проверка с сервера» с этим адресом и ресурсом «VPN офис». Скопируйте секрет.

3. Запустите проверку для пользователя с привязанным телефоном:

   ```bash
   sudo mfagatectl radius-test ivanov
   ```

   Команда спросит `shared secret:` (секрет клиента «Проверка с сервера») и `пароль:` пользователя. Подтвердите запрос на телефоне.

**Ожидаемый результат:**

```json
{"result": "accept", "authenticator_ok": true, "message": "", "seconds": 7.4}
```

| `result` | Что значит |
|---|---|
| `accept` | вход разрешён |
| `reject` | отказ; причина — в «Истории входов» |
| `challenge` | MFA Gate просит код TOTP (у пользователя нет телефона или политика разрешает только TOTP). Проверка кода этой командой не выполняется — успешный `challenge` уже подтверждает, что пароль и политика в порядке |
| `timeout` | ответа нет: неверный секрет, нет клиента для подсети Docker, сервис `radius` не работает |

`authenticator_ok: false` означает, что ответ подписан другим секретом.

4. После проверки отключите или удалите клиент «Проверка с сервера».

Эта проверка не проходит через порт хоста и межсетевой экран. Сеть проверяется следующим шагом.

## Шаг 6. Проверка со стороны шлюза

На любой машине Linux в сети шлюза (адрес которой заведён как RADIUS-клиент) можно отправить запрос утилитой `radclient` из пакета `freeradius-utils`:

```bash
sudo apt-get install -y freeradius-utils
printf 'User-Name = "ivanov"\nUser-Password = "пароль"\nMessage-Authenticator = 0x00\n' \
  | radclient -x -t 60 -r 1 192.0.2.10:1812 auth 'СЕКРЕТ'
```

Строка `Message-Authenticator = 0x00` заставляет `radclient` вычислить и добавить атрибут. Подтвердите вход на телефоне.

**Ожидаемый результат:** `Received Access-Accept`.

Если ответа нет — см. [Диагностика](Диагностика.md), раздел «RADIUS не отвечает». Затем настройте шлюз: [Подключение VPN](Подключение-VPN.md).
