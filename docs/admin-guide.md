# Руководство администратора

Справочник по модели входа, объектам, политикам, ролям и кодам причин. Пошаговые инструкции (первый вход, подключение AD, RADIUS, телефоны, TOTP) — в Wiki: [Первоначальная настройка](../wiki/Первоначальная-настройка.md). Установка и команды сервера — [install.md](install.md); устройство панели — [admin-ui.md](admin-ui.md); сеть и публикация — [network.md](network.md). Панель открывается по адресу `/admin/`, личный кабинет сотрудника — по `/` ([Личный кабинет сотрудника](../wiki/Личный-кабинет-сотрудника.md)). Всё, что делает панель, доступно и через REST API ([api.md](api.md)).

## Как проходит вход

1. **Блокировка.** Если учётная запись временно заблокирована после ошибок, следует отказ `locked`. По умолчанию это 8 ошибок подряд и блокировка на 15 минут.
2. **Первый фактор.** Локальный пользователь проверяется по паролю в MFA Gate. Остальные проверяются в каталогах LDAP/AD по возрастанию приоритета. Каталог, из которого пользователь уже пришёл, проверяется первым. Если у RADIUS-клиента «Первый фактор» — `gateway`, пароль проверил шлюз: MFA Gate его не проверяет, пустой пароль запускает второй фактор, 6–8 цифр проверяются как код TOTP ([integrations.md](integrations.md#первый-фактор-mfa_gate-и-gateway)).
3. **Политика.** Выбирается по ресурсу и группам пользователя (см. «Модель политик»).
4. **Второй фактор** — в таком порядке:
   - push, если политика разрешает `push` и у пользователя есть привязанный телефон;
   - иначе Access-Challenge (запрос кода TOTP), если политика разрешает `totp` и у пользователя есть подтверждённый TOTP;
   - иначе отказ `no_factor`, если политика не разрешает вход без фактора (`on_unavailable=allow`).

У пользователя с привязанным телефоном вход по RADIUS всегда идёт через push, даже если ему выдан TOTP. Чтобы на каком-то ресурсе спрашивать код, оставьте в политике этого ресурса только метод `totp`. Через REST API приложение может сразу передать код в поле `otp`.

## Объекты

Порядок настройки по шагам: [Первоначальная настройка](../wiki/Первоначальная-настройка.md).

### 1. Каталог LDAP / AD

Поля, порядок входа, обработка групп и коды ошибок каталога — [ldap.md](ldap.md). Пошаговое подключение Active Directory с диагностикой и подкодами AD — [Подключение Active Directory](../wiki/Подключение-Active-Directory.md).

Если ни один контроллер не ответил, вход отклоняется (`directory_unavailable`), пропуска без проверки пароля нет.

### 2. Ресурс

Ресурс — то, куда входят: «VPN офис», «Портал». Тип `vpn`, `app` или `other`. Политики и журнал ссылаются на ресурс. Отключённый ресурс отклоняет все входы (`resource_disabled`).

### 3. RADIUS-клиент и секрет

RADIUS-клиент — это VPN-шлюз. Он привязан к ресурсу:

- **Адрес** — IP или сеть, с которой приходят пакеты (с учётом NAT между шлюзом и MFA Gate). Если адрес подходит под несколько клиентов, выбирается самая узкая сеть. Один и тот же адрес нельзя назначить двум клиентам.
- **Секрет** — 16–128 символов. Если поле оставить пустым, секрет сгенерируется. Он показывается один раз, на сервере хранится зашифрованным.
- **NAS-Identifier** — необязательно. Если задан, пакеты с другим значением отбрасываются.
- **Первый фактор** (`first_factor`) — `mfa_gate` (по умолчанию): MFA Gate проверяет пароль сам, PAP. `gateway`: шлюз уже проверил доменный пароль, MFA Gate доверяет этому только для этого клиента. Ставьте `gateway` только шлюзу, который действительно проверяет пароль сам ([ADR 0016](adr/0016-first-factor-per-radius-client.md)).

Изменения вступают в силу в течение 15 секунд, перезапуск не нужен. Пошагово: [Настройка RADIUS](../wiki/Настройка-RADIUS.md); правила протокола — [integrations.md](integrations.md).

### 4. Политика

Без политик действует правило по умолчанию: второй фактор обязателен для всех, разрешены push и TOTP. Политики нужны для исключений: запретить ресурс группе, оставить только TOTP, пропустить сервисную учётную запись.

### 5. Пользователи

- **Из каталога.** Специально заводить не нужно: запись создаётся при первом успешном входе и дальше связывается по устойчивому идентификатору (`objectGUID`/`entryUUID`). Имя, e-mail, телефон и группы обновляются при каждом входе. Чтобы привязать телефон до первого входа, создайте пользователя с источником `ldap` и тем же логином.
- **Локальные** — для тех, кого нет в каталоге. Пароль не короче 12 символов.
- **Группы MFA Gate** — локальные группы. Группу можно сопоставить группе каталога (поле «группа каталога», CN или DN), тогда её получают все члены этой группы.

### 6. Второй фактор пользователя

- **Телефон (push)** — «Привязать телефон» в карточке: одноразовый QR-код на 24 часа (`MFA_GATE_ENROLLMENT_TTL_HOURS`) с адресом `MFA_GATE_PUBLIC_URL`. Пошагово: [Регистрация Android-устройства](../wiki/Регистрация-Android-устройства.md).
- **TOTP** — «Выпустить» в блоке TOTP карточки; фактор работает после подтверждения первым кодом. Пошагово: [Настройка TOTP](../wiki/Настройка-TOTP.md).
- **Отозвать** телефон или удалить TOTP можно в той же карточке. Отозванное устройство сразу теряет доступ.
- **Самостоятельно** — сотрудник подключает факторы в личном кабинете. По одному паролю — только если у него никогда не было фактора, из сетей `MFA_GATE_PORTAL_ENROLL_NETWORKS` и для групп `MFA_GATE_PORTAL_ENROLL_GROUPS`; добавочные факторы — после входа со вторым фактором. Резервные коды (10 одноразовых, показываются один раз) действуют только для входа в кабинет ([ADR 0017](adr/0017-self-enrollment-and-recovery.md)).
- **Разрешить повторную регистрацию** — действие в карточке для сотрудника, потерявшего телефон без резервных кодов: одноразовое разрешение на 24 часа пройти мастер в кабинете заново по паролю. Потерянное устройство отзовите отдельно.

На панели состояния показано, сколько пользователей не имеют ни одного фактора. Пока у них нет фактора, их входы отклоняются с причиной `no_factor`.

## Модель политик

| Поле | Значение |
|---|---|
| `priority` | меньше — раньше. Политики проверяются по возрастанию, применяется **первая совпавшая** |
| `enabled` | выключенные не участвуют |
| `resource_ids` | пусто — любой ресурс; иначе только перечисленные. Запросы REST API без ресурса совпадают только с политиками без ресурсов |
| `groups` | пусто — все пользователи; иначе пользователь должен входить хотя бы в одну |
| `exclude_groups` | если пользователь входит хотя бы в одну, политика пропускается |
| `action` | `mfa` — нужен второй фактор; `allow` — вход по одному паролю; `deny` — отказ (`policy_deny`) |
| `methods` | для `mfa`: `push`, `totp` или оба |
| `on_unavailable` | `deny` (по умолчанию) или `allow` — что делать, если у пользователя нет подходящего фактора |

- Группы сравниваются без учёта регистра. В условиях можно указывать имя группы MFA Gate, CN или DN группы каталога.
- **Нет совпадений — второй фактор обязателен** (push и TOTP, `on_unavailable=deny`).
- `action=allow` пропускает вход без второго фактора. Такой вход пишется в историю со статусом `allowed` и причиной `policy_allow`.
- `on_unavailable=allow` — **риск**: пользователь без телефона и TOTP входит по одному паролю. Каждый такой вход пишется в журнал аудита с уровнем `warning` и причиной `mfa_bypass_unavailable`. Используйте его временно, на период раздачи телефонов, и ограничивайте группой.
- Вход администратора в панель всегда требует второй фактор, политики на него не влияют.

Пример набора:

| priority | Имя | Условия | Действие |
|---|---|---|---|
| 10 | Подрядчикам VPN закрыт | ресурс «VPN офис», группа `contractors` | `deny` |
| 20 | Сервисная учётная запись мониторинга | ресурс «VPN офис», группа `svc-monitoring` | `allow` |
| 30 | Только код для старого шлюза | ресурс «VPN филиал» | `mfa`, `totp` |
| — | все остальные | — | `mfa`, push и TOTP (по умолчанию) |

## Роли администраторов

Роль назначается пользователю в карточке. Назначать и снимать роли может только тот, у кого есть право `admins:write`, то есть `superadmin`. Последнего активного `superadmin` нельзя лишить роли, отключить или удалить.

| Роль | Права |
|---|---|
| `superadmin` — главный администратор | всё, включая управление администраторами |
| `admin` — администратор | чтение и изменение всех разделов (пользователи, группы, устройства, ресурсы, политики, RADIUS, LDAP, ключи API, система). Администраторов только видит |
| `operator` — оператор | пользователи и устройства (чтение и изменение: привязка телефона, TOTP, разблокировка); группы, ресурсы, политики, история, аудит, состояние — только чтение |
| `auditor` — аудитор | только чтение всех разделов, включая журнал аудита |

Права записываются как `<область>:read|write`. Те же строки служат scopes ключей API ([api.md](api.md#права-scopes)).

## Аварийный доступ

Если администратор потерял телефон и TOTP, войти в панель он не сможет. На сервере выполните:

```bash
sudo mfagatectl emergency <логин>
```

Команда печатает одноразовый код. Он действует 15 минут и один раз заменяет второй фактор при входе этого администратора в панель (пароль по-прежнему нужен). Выдача и использование кода пишутся в журнал аудита с уровнем `critical` (`admin.emergency_code_issued`, `admin.emergency_access`). После входа сразу выпустите новый TOTP в своей карточке (или попросите другого главного администратора). Повторная первичная настройка TOTP на экране входа недоступна, если у учётной записи есть подключённый TOTP или когда-либо был привязан телефон (даже отозванный): так оператор не может подменить фактор администратора. Пошагово: [Создание администратора](../wiki/Создание-администратора.md#восстановление-доступа).

Если забыт и пароль локального администратора, `sudo mfagatectl admin <логин>` задаст новый. Новых администраторов назначают в панели: роль в карточке пользователя.

## История входов

В истории видны каждая попытка входа, канал (`radius`, `api`), ресурс, клиент (шлюз или приложение), адрес клиента (`Calling-Station-Id`), адрес шлюза, метод (`push`, `totp`, `policy`), результат, причина и время ответа. Экран проблем входа группирует отказы за последние дни по пользователю и причине.

Статусы: `approved` — подтверждено вторым фактором; `allowed` — пропущено политикой; `rejected`, `denied`, `expired` — отказ; `pending` — ожидание.

| Код причины | Значение | Что делать |
|---|---|---|
| `local_password` | Неверный логин или пароль (локальная учётная запись) | проверить пароль; после 8 ошибок — блокировка |
| `ldap_password` | Каталог не принял пароль | пароль в каталоге |
| `unknown_user` | Пользователь не найден ни локально, ни в каталогах | логин, `user_filter`, `base_dn`; нет включённых каталогов |
| `user_disabled` | Учётная запись отключена | включить в MFA Gate или в каталоге |
| `locked` | Временная блокировка после ошибок входа | подождать или «Разблокировать» в карточке |
| `directory_unavailable` | Каталог LDAP/AD недоступен — вход запрещён | диагностика каталога, сеть, сертификат |
| `directory_denied` | Каталог отклонил вход (учётная запись заблокирована, пароль истёк или нет нужной группы) | состояние учётной записи в каталоге, `allowed_groups` |
| `policy_deny` | Доступ запрещён политикой | какая политика совпала |
| `no_factor` | У пользователя нет доступного второго фактора | привязать телефон или выдать TOTP; проверить `methods` политики |
| `invalid_otp` | Неверный или уже использованный одноразовый код | время на телефоне; код нельзя использовать повторно |
| `push_denied` | Пользователь отклонил запрос | уточнить у сотрудника; если входил не он — сменить пароль |
| `push_expired` | Нет ответа на push в отведённое время | доставка push, сеть телефона, таймаут шлюза |
| `resource_disabled` | Ресурс отключён | включить ресурс |
| `policy_allow` | вход пропущен политикой `allow` (не отказ) | — |
| `mfa_bypass_unavailable` | вход без второго фактора по `on_unavailable=allow` (не отказ, `warning`) | раздать факторы и выключить режим |

Если на `push_denied` сотрудник отвечает «это был не я», значит, его пароль известен постороннему. Смените пароль, проверьте историю входов этого пользователя.

## Журнал аудита

Журнал записывает действия администраторов и важные события безопасности: создание и изменение объектов, вход в панель, выдачу ссылок привязки и TOTP, отвязку устройств, выпуск и ротацию ключей API, отклонённые RADIUS-пакеты (`radius.bad_authenticator`), неверные подписи устройств (`device.bad_signature`), аварийный доступ. Каждая запись содержит время, событие, уровень (`info`, `warning`, `critical`), кто, над чем, адрес, результат и подробности. Секреты в журнал не пишутся.

Фильтры: префикс события (`auth.`, `admin.`, `device.`), автор, уровень, результат. Выгрузка — CSV (`/api/v1/audit/export.csv`, до 100 000 записей). Значения, начинающиеся с `= + - @`, экранируются от формульных инъекций.

Журнал хранится 365 дней, история входов — 180 дней (`MFA_GATE_AUDIT_RETENTION_DAYS`, `MFA_GATE_AUTH_REQUEST_RETENTION_DAYS`). Если нужен более долгий срок, регулярно выгружайте CSV.
