# Android-приложение MFA Gate Authenticator

Исходники: `android/`. Сборка, подпись и flavors: `android/README.md`. Контракт с сервером: `docs/protocol/device-api.md`.

Версия 0.1.0. Пакет `mfa_gate.authenticator`, minSdk 26, targetSdk 36, compileSdk 37.

## Что умеет

1. **Привязка к серверу.** QR-код `mfagate://enroll` (сканер zxing-android-embedded, без ML Kit и сервисов Google) или ссылка, вставленная вручную. Экран подтверждения показывает адрес сервера и `label`. Затем приложение создаёт ключ EC P-256 в AndroidKeyStore и отправляет `POST /api/device/v1/enroll`. Можно привязать несколько серверов.
2. **Запросы входа.** Экран «Запросы» держит long-poll по каждому серверу, пока он на переднем плане (`LifecycleStartEffect`: при уходе в фон запросы отменяются вместе с HTTP-вызовом). Карточка запроса показывает логин, ресурс, IP, место, клиент, время и обратный отсчёт до `expires_at`. «Подтвердить» и «Отклонить» подписываются через BiometricPrompt с `CryptoObject(Signature)`.
3. **Уведомления.** Канал `auth_requests` с `IMPORTANCE_HIGH`. Разрешение `POST_NOTIFICATIONS` запрашивается на Android 13+ (плашка на экранах «Запросы» и «Настройки»). Уведомление только открывает экран запроса: действия, которое подтверждает вход без биометрии, нет. На заблокированном экране показывается версия без подробностей. Уведомление само исчезает к `expires_at`.
4. **TOTP.** `otpauth://totp` (SHA1/SHA256/SHA512, 6 или 8 цифр, период 1–300 с, по умолчанию 30) из QR или ручной ввод. Коды крупным моноширинным шрифтом, круговой таймер, копирование по нажатию с пометкой «чувствительные данные» для буфера обмена. Работает без сети. Реализация RFC 6238 своя, на `javax.crypto.Mac`.
5. **История** (`GET /requests?limit=50`), **отвязка** (`DELETE /self`; при 401 учётная запись удаляется локально; если сервер недоступен, можно удалить только на телефоне), **настройки**: блокировка приложения биометрией или PIN при открытии и после 30 с в фоне.

## Архитектура

Одна Activity (`MainActivity : FragmentActivity`, это нужно BiometricPrompt), Jetpack Compose + Material3, Navigation Compose, ViewModel + StateFlow. DI-фреймворка нет: зависимости процесса живут в `App` (`vault`, `api`, `scope`, `locked`).

| Пакет | Содержимое | Тесты |
| --- | --- | --- |
| `core/` | чистый Kotlin без Android: `Totp`, `Base32`, `Base64Url`, `Links` (разбор `otpauth://` и `mfagate://enroll`, нормализация адреса сервера), `DecisionString`, модели протокола (kotlinx.serialization), `ApiException` с текстами ошибок на русском | JVM |
| `net/` | интерфейс `DeviceApi` и реализация `HttpDeviceApi` на OkHttp: `await()` с отменой, без перенаправлений, отдельный клиент с таймаутом чтения 45 с для long-poll | JVM, MockWebServer |
| `data/` | `SecretBox` (интерфейс `Sealer`), `DeviceKeys`, интерфейс `Vault` и `PrefsVault` на SharedPreferences | на устройстве |
| `push/` | `Notifier`, `PollWorker` (WorkManager); в flavor-каталогах — `Push` (`foss`: только WorkManager; `gms`: FCM) и `MfaGateMessagingService` | на устройстве |
| `ui/` | экраны, `Biometrics`, `theme/Theme.kt` | вручную |

Дизайн-система собрана в одном файле `ui/theme/Theme.kt`. Отступы берутся из шкалы `Space` (4/8/12/16/24/32), тап-цели не меньше `MinTap` = 48dp. Светлая и тёмная схемы: графитовый или светлый фон и один акцент, бирюзово-зелёный. Для кодов используется `CodeStyle`, моноширинный 34sp. Карточки плоские, без теней и градиентов. Общие компоненты лежат в `ui/Components.kt`: `ScreenScaffold`, `PrimaryButton`, `SecondaryButton`, `Panel`, `InfoRow`, `StateMessage` (пусто или ошибка), `Loading`, `ErrorText`, `SecureWindow`.

## Ключи и секреты

| Что | Где | Как защищено |
| --- | --- | --- |
| Ключ подтверждения ECDSA P-256 | AndroidKeyStore, алиас `mfa_gate_device_<uuid>`, по одному на сервер | `PURPOSE_SIGN`, `DIGEST_SHA256`, `setUserAuthenticationRequired(true)`. На API 30+ `setUserAuthenticationParameters(0, BIOMETRIC_STRONG or DEVICE_CREDENTIAL)`: подтверждение на каждую подпись биометрией или PIN. На API 26–29 `setUserAuthenticationValidityDurationSeconds(-1)`: только сильная биометрия через `CryptoObject`. Если есть StrongBox, ключ создаётся в нём, иначе в TEE. `setInvalidatedByBiometricEnrollment` оставлен по умолчанию (true): после смены отпечатков ключ становится недействителен, и приложение просит привязать устройство заново |
| Открытый ключ | сервер | SPKI DER, base64url, в `public_key` при привязке |
| `device_secret` | SharedPreferences | AES-256-GCM ключом `mfa_gate_secrets` из AndroidKeyStore (`SecretBox`), AAD `device.<id учётной записи>` |
| Секреты TOTP | SharedPreferences | тот же `SecretBox`, AAD `totp.<id>` |

Подпись решения строится так. Строка `mfa-gate-decision-v1\n<request_id>\n<device_id>\n<challenge>\n<approve|deny>` в UTF-8, без завершающего перевода строки. Поля с `\n` или `\r` отвергаются, чтобы строку нельзя было сдвинуть. Подпись `SHA256withECDSA` (Keystore выдаёт её сразу в DER) кодируется в base64url без выравнивания. Тест `DecisionTest` проверяет подпись по SPKI так же, как это будет делать сервер.

`allowBackup=false` и `data_extraction_rules.xml` исключают данные из облачной копии и переноса на другое устройство: ключи Keystore там не восстановятся. Экраны с кодами (`Коды`, `Новый код`) ставят `FLAG_SECURE`.

**Сеть.** В release разрешён только HTTPS (`network_security_config`) и только системные CA. Пользовательские сертификаты для фактора аутентификации сознательно не принимаются, хотя в «Переговорке» они разрешены. Если организации нужен свой CA, его ставят как системный через MDM, либо нужно отдельное решение (ADR). Debug-сборка разрешает HTTP и пользовательские CA для тестового стенда, и адрес `http://` в ссылке привязки принимается только в debug (`BuildConfig.DEBUG`). Перенаправления выключены, чтобы заголовок `Authorization: Device …` не ушёл на другой адрес. Для запросов используется адрес из ссылки, которую подтвердил пользователь, а не `server.url` из ответа `/enroll`.

## Push и фоновая проверка

- **foss.** Пока экран «Запросы» открыт, работает long-poll. В фоне `PollWorker` раз в 15 минут (минимум WorkManager, нужна сеть) делает `wait=0` по всем серверам и показывает уведомления о запросах, о которых ещё не уведомлял (последние 200 id хранятся в настройках). Для подтверждения входа это медленно, поэтому основной сценарий такой: пользователь сам открывает приложение после попытки входа.
- **gms.** `FirebaseApp` по умолчанию создаётся вручную из `push_config.fcm` первой учётной записи, у которой он есть (`FirebaseOptions.Builder`). `FirebaseInitProvider` удалён из манифеста. Токен уходит на `PUT /api/device/v1/push` после привязки, при каждом запуске и в `onRegistered`/`onNewToken`. При получении `{type: "auth_request", request_id}` приложение загружает `GET /requests/{id}` с серверов, которые используют этот проект Firebase, и показывает уведомление. `PollWorker` работает и здесь как запасной путь, повторные уведомления отсекаются по id.
- Ограничение: один `FirebaseApp` на процесс. Серверы с другим проектом Firebase получают запросы только через long-poll и WorkManager (`shortcut:` в `gms/.../Push.kt`).

## Что проверено

На сервере сборки нет эмулятора и KVM, поэтому проверено только то, что выполняется без устройства:

- `./gradlew :app:testFossDebugUnitTest :app:testGmsDebugUnitTest`: 28 JVM-тестов в каждом варианте, без падений. Покрыты векторы RFC 6238 (SHA1/SHA256/SHA512), base64url и Base32 по RFC 4648, разбор `otpauth` и `mfagate://enroll` (27 некорректных ссылок отвергаются), строка подписи и подпись P-256 с проверкой по SPKI, клиент Device API на MockWebServer.
- `assembleFossDebug`, `assembleGmsDebug`, `assembleFossRelease`, `assembleGmsRelease` (R8) и `lintFossDebug`/`lintGmsDebug` проходят без ошибок. Lint нашёл и помог исправить вызов `URLDecoder.decode(String, Charset)`, которого нет до API 33.
- В APK `foss` нет классов `com.google.firebase` и `com.google.android.gms`. В манифесте `gms` есть `MfaGateMessagingService`, а `FirebaseInitProvider` отсутствует.

## Что требует проверки на реальном устройстве

1. Создание ключа и подпись через BiometricPrompt на API 26–29 (только отпечаток) и на API 30+ (отпечаток и PIN). Отдельно проверить устройство со StrongBox и поведение после добавления отпечатка (`KeyPermanentlyInvalidatedException` → сообщение «привяжите заново»).
2. Привязка к настоящему серверу. Сервер Device API на момент написания ещё не реализован, приложение сделано по документу протокола.
3. FCM: ручная инициализация `FirebaseApp` из `push_config`, получение токена, доставка data-сообщения при выгруженном приложении и в режиме Doze, поведение `register()`/`onRegistered` в firebase-messaging 26.
4. WorkManager: периодичность и уведомления на устройствах с агрессивной экономией энергии.
5. Сканер QR (zxing-android-embedded) на разных камерах, поворот экрана.
6. `FLAG_SECURE` на экранах кодов, блокировка приложения после 30 с в фоне, возврат из системного экрана PIN на API < 30.
7. Обновление поверх (versionCode из `VERSION`) и подпись постоянным ключом.

## Замечания к протоколу (не изменён, требует решения)

1. **Long-poll при уже существующем pending-запросе.** Сервер отвечает сразу, если pending-запрос есть, поэтому без курсора клиент крутится в цикле. Приложение делает паузу 3 с, если список не пуст. Нужен курсор (`since`/`etag`/`known=`), чтобы ждать именно изменений.
2. **В push-сигнале нет устройства.** Сигнал `{type, request_id}` не говорит, к какому серверу или устройству он относится. При нескольких учётных записях на одном проекте Firebase приложение опрашивает `GET /requests/{id}` у каждой, пока не найдёт нужную (у чужих 404). Предлагается добавить `device_id`.
3. **Несколько проектов Firebase.** `push_config` задаётся на сервере, а FCM даёт один `FirebaseApp` по умолчанию и один токен на приложение. Серверы разных организаций с разными проектами Firebase не могут получать push одновременно, протокол этот случай не описывает.
4. **Нет времени сервера.** Обратный отсчёт до `expires_at` идёт по часам телефона. Если часы сбиты, отсчёт неверен. Кнопки при этом не блокируются: последнее слово за сервером (410). Предлагается поле `server_time` в ответах.
5. **Формат тела ошибки не закреплён.** Коды вроде `already_decided` есть, а JSON-обёртки нет. Приложение ищет код в `error`, `code` или `detail`. Предлагается закрепить `{"error": "<code>", "message": "..."}`.
6. **`push_config` в ответе `/enroll`** упомянут только в §7 и отсутствует в примере §2. Приложение принимает его, а если поля нет, запрашивает `GET /config`.
7. **Чей адрес главный, `server.url` из `/enroll` или из QR,** не сказано. Приложение использует адрес из QR, который подтвердил пользователь.
8. **Нет аттестации ключа (key attestation).** Сервер не может проверить, что ключ аппаратный и требует подтверждения пользователем. Предлагается необязательное поле `attestation` (цепочка сертификатов) в `/enroll` с challenge от сервера.
9. **§6 описывает действия «Подтвердить/Отклонить» в уведомлении.** Приложение намеренно оставляет одно действие «Открыть запрос», а решение принимается на экране с подробностями и биометрией. В протоколе стоит описать это как допустимый вариант.
10. **Ответы `DELETE /self` и `PUT /push`** не описаны. Приложение считает успехом любой 2xx, а 401 при отвязке — тоже успехом.
11. **`429 rate_limited`** описан только для `/enroll`, `Retry-After` не упомянут. Приложение отступает экспоненциально, до 60 с.
