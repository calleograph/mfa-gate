# 0015. Внешняя публикация Device API и защита по имени хоста

**Контекст.** Телефон подтверждает вход в VPN, когда VPN ещё не поднят: сотрудник дома, телефон в мобильной сети. Значит, Device API должен быть доступен из Интернета. Кабинет, панель и REST API наружу открывать незачем: это лишняя поверхность атаки (подбор паролей, уязвимости веб-интерфейса).

**Решение.**
- `MFA_GATE_PUBLIC_URL` — внутренний адрес кабинета и панели. `MFA_GATE_DEVICE_URL` — внешний HTTPS-адрес для телефонов; он попадает в QR-код привязки. По умолчанию равен `MFA_GATE_PUBLIC_URL`.
- Reverse proxy публикует внешнее имя только с префиксом `/api/device/`, остальное — 404. Примеры: `deploy/proxy/nginx.conf`, `deploy/proxy/Caddyfile`.
- Второй рубеж в самом сервере: если хост `MFA_GATE_DEVICE_URL` отличается от хоста `MFA_GATE_PUBLIC_URL`, на любой запрос с заголовком `Host`, равным внешнему имени, и путём не из `/api/device/…` или `/health/…` сервер отвечает 404.
- Внутреннее имя ограничивается в прокси по адресам источника.

**Последствия.** Ошибка в конфигурации прокси (забытый `location`) не открывает панель наружу. Проверка по `Host` работает, только если прокси передаёт исходный `Host`. Она не защищает внутреннее имя: запрос из Интернета с `Host: mfa.example.org` на общий прокси закрывается только правилами прокси. Смена `MFA_GATE_DEVICE_URL` требует перепривязки телефонов. Device API снаружи защищён тем же, что и раньше: одноразовые токены привязки, `device_secret`, подпись решения ключом Keystore, лимиты частоты.

**Альтернативы.** Всё приложение наружу — проще, но открывает панель и кабинет для подбора паролей. Только внутренняя публикация — телефон не подтвердит вход до VPN (работает лишь с офисным Wi-Fi). Отдельный порт или процесс для Device API — ещё один сервис и порт при том же коде; разделение по имени и префиксу проще и укладывается в существующий прокси. Отдельный ретранслятор в облаке — третья сторона в цепочке доверия.
