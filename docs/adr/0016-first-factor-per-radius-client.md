# 0016. Источник первого фактора у RADIUS-клиента (режим gateway)

**Контекст.** MFA Gate проверял пароль сам и требовал PAP. Часть шлюзов сама проверяет доменный пароль, а внешний RADIUS-сервер спрашивает только про второй фактор. Типичные режимы таких шлюзов: «только логин» — логин с пустым паролем, «логин и одноразовый код» — логин и код. Раньше такие шлюзы подключить было нельзя.

**Решение.** Поле RADIUS-клиента `first_factor` («Первый фактор»):
- `mfa_gate` (по умолчанию) — MFA Gate проверяет пароль сам (каталог LDAP/AD или локально), PAP;
- `gateway` — шлюз уже проверил пароль; MFA Gate доверяет этому только для этого зарегистрированного клиента. В этом режиме:
  - пустой `User-Password` — сценарий второго фактора: push с удержанием запроса до решения или Access-Challenge для TOTP;
  - `User-Password` из 6–8 цифр — код TOTP;
  - любое другое значение не проверяется как пароль и не считается ошибкой входа — запрос идёт как с пустым паролем.

Глобального пропуска первого фактора нет: режим задаётся только у конкретного клиента. Пользователь должен быть известен MFA Gate (создан заранее или пришёл из каталога). Блокировка, политики, история и аудит работают как обычно.

**Последствия.** Доверие к клиенту в режиме `gateway` выше: кто может отправить пакет от его имени, тот получает push или проверку кода без пароля. Поэтому обязательны свой длинный секрет на каждый клиент, Message-Authenticator и фильтрация UDP 1812 по адресу источника; между площадками — IPsec или WireGuard. Ошибки пароля в этом режиме видит только шлюз, в истории MFA Gate их нет. Режим не помогает шлюзам, которые пересылают MS-CHAPv2 (например, NPS в режиме пересылки): им нужен PAP и режим `mfa_gate`.

**Альтернативы.** Глобальная настройка «пароль проверяет шлюз» — один ошибочный клиент или подделанный адрес снимал бы первый фактор для всех. Режим «пароль и код в одном поле» — не решает случай шлюза, который не передаёт пароль; остаётся в планах. Прокси на FreeRADIUS с отдельной логикой — лишний сервис ([0006](0006-radius.md)).
