# Подключение VPN-шлюзов и приложений

Справочник по протоколу RADIUS в MFA Gate и по запросу входа через REST API. Пошаговая настройка: [Настройка RADIUS](../wiki/Настройка-RADIUS.md) (ресурс, клиент, секрет, проверка), [Подключение VPN](../wiki/Подключение-VPN.md) (OpenVPN, Windows NPS/RRAS, Cisco, FortiGate, MikroTik, pfSense), [Шлюзы с собственной проверкой пароля](../wiki/Шлюзы-с-собственной-проверкой-пароля.md), [Интеграция по REST API](../wiki/Интеграция-по-REST-API.md). Порты, публикация и межсетевой экран — [network.md](network.md).

Состояние: протокол RADIUS покрыт сквозными тестами в Docker. **Настройки конкретных шлюзов не проверены на реальном оборудовании** — они собраны по документации производителей и помечены «требует проверки на реальном шлюзе». Если вы проверили шлюз, пришлите исправления (см. [CONTRIBUTING.md](../CONTRIBUTING.md)).

## Общие правила RADIUS

| Что | Как в MFA Gate |
|---|---|
| Порт | UDP 1812 (`MFA_GATE_RADIUS_PORT` на хосте). Accounting (1813) **не реализован**: выключите его на шлюзе или направьте в другую систему |
| Клиент | определяется по адресу источника пакета. Неизвестный адрес — пакет молча отбрасывается, шлюз видит таймаут |
| Метод пароля | только **PAP**. На CHAP/MS-CHAPv2 MFA Gate отвечает Access-Reject «Поддерживается только PAP». В режиме `first_factor=mfa_gate` (по умолчанию) MFA Gate сам проверяет пароль (локально или в LDAP/AD), поэтому ему нужен пароль в открытом виде внутри RADIUS. Если пароль проверяет шлюз — режим `gateway` (ниже) |
| Первый фактор | поле RADIUS-клиента «Первый фактор»: `mfa_gate` или `gateway`, см. [ниже](#первый-фактор-mfa_gate-и-gateway) |
| Message-Authenticator | **обязателен** (защита от BlastRADIUS). Пакет без него или с неверным значением отбрасывается, в аудите появляется `radius.bad_authenticator`. Для старого шлюза его можно отключить через `MFA_GATE_RADIUS_REQUIRE_MESSAGE_AUTHENTICATOR=false`, но это ослабляет защиту |
| NAS-Identifier | если задан у клиента в MFA Gate, должен совпадать, иначе пакет отбрасывается |
| Calling-Station-Id | показывается сотруднику в запросе как IP-адрес входа. Настройте шлюз так, чтобы он его передавал |
| Атрибуты ответа | Access-Accept не содержит Class, Filter-Id, VSA. Назначение групп или пулов по ответу RADIUS **не реализовано** |

### Таймаут и повторы

Push держит Access-Request открытым, пока сотрудник не ответит или не истечёт `MFA_GATE_PUSH_TIMEOUT` (по умолчанию 45 с). Поэтому:

- **таймаут RADIUS на шлюзе ≥ `MFA_GATE_PUSH_TIMEOUT` + 15 с**, при значении по умолчанию — 60 с;
- 1–2 повтора. Повтор того же пакета (тот же адрес, Identifier и Request Authenticator) в течение 90 с не создаёт новый вход и не шлёт второй push: MFA Gate ждёт ту же обработку и отвечает тем же. Новый Access-Request того же пользователя к тому же ресурсу с того же адреса, пока push ещё ждёт ответа, присоединяется к этому push;
- если шлюз ограничивает таймаут (например, 10 с), уменьшите `MFA_GATE_PUSH_TIMEOUT` или используйте TOTP через Access-Challenge.

Если таймаут шлюза меньше времени ответа, сотрудник подтверждает вход на телефоне, а VPN-клиент уже показывает ошибку.

### Access-Challenge (код TOTP)

Если политика ресурса допускает TOTP, а push не используется (у пользователя нет телефона или в политике только `totp`), MFA Gate отвечает:

```
Access-Challenge
  Reply-Message  = "Введите одноразовый код"
  State          = <16 байт, идентификатор попытки>
  Session-Timeout = 120        (MFA_GATE_OTP_CHALLENGE_TIMEOUT)
```

Шлюз показывает Reply-Message и отправляет новый Access-Request с тем же `User-Name`, атрибутом `State` и кодом в `User-Password`. Код проверяется один раз, повтор того же кода отклоняется (`invalid_otp`).

Reply-Message передаётся в UTF-8 на русском. Проверьте, что клиент VPN показывает его без искажений.

Режим «пароль и код в одной строке» по RADIUS **не реализован**. Режим «только второй фактор», когда пароль проверил шлюз, — `first_factor=gateway`.

### Первый фактор: `mfa_gate` и `gateway`

Задаётся у каждого RADIUS-клиента отдельно (поле «Первый фактор»). Глобального пропуска проверки пароля нет. Решение — [ADR 0016](adr/0016-first-factor-per-radius-client.md).

| `User-Password` в Access-Request | `mfa_gate` (по умолчанию) | `gateway` |
|---|---|---|
| пароль | проверяется в каталоге или локально | не проверяется, ошибкой не считается; дальше — как пустой |
| пусто | отказ | второй фактор: push с удержанием запроса до решения или Access-Challenge для TOTP |
| 6–8 цифр | проверяется как пароль | проверяется как код TOTP |

- `gateway` ставьте, только если шлюз **сам** проверяет доменный пароль до запроса в MFA Gate. Иначе любой, кто знает логин, получит push сотруднику без пароля.
- Запись и группы доменного сотрудника MFA Gate при каждом запросе берёт из каталога сервисной учётной записью: новый сотрудник заводится сам, отключённый в каталоге, удалённый из него или вне разрешённых групп получает отказ `directory_denied`. Каталог не отвечает — отказ `directory_unavailable`; у каталога нет сервисной учётной записи — используется сохранённая запись. Второй фактор у сотрудника должен быть: подключается в личном кабинете или администратором.
- Ошибки пароля в режиме `gateway` видит только шлюз; в «Истории входов» MFA Gate их нет.
- Требования к клиенту в этом режиме строже: свой длинный секрет, Message-Authenticator, UDP 1812 открыт только адресу шлюза, между площадками — IPsec или WireGuard ([network.md](network.md#правила-межсетевого-экрана)).
- Шлюз, который пересылает MS-CHAPv2 (NPS в режиме пересылки), этот режим не выручает: пароль из MS-CHAPv2 не извлечь, а пустого пароля или кода в PAP такой шлюз не присылает.

## Шлюзы

| Шлюз | Как подключается | PAP | Access-Challenge (код TOTP) | Статус |
|---|---|---|---|---|
| OpenVPN 2.5+ (скрипт `integrations/openvpn/mfa-gate-openvpn.sh`) | REST API, отложенная проверка | — | через `static-challenge` | требует проверки на реальном шлюзе |
| OpenVPN (`openvpn-plugin-auth-pam` + `pam_radius`) | RADIUS | да | зависит от версий плагина и клиента | требует проверки на реальном шлюзе |
| Windows NPS / RRAS | RADIUS через NPS | только для клиентов с PAP; MS-CHAPv2/EAP не работают | нет данных | требует проверки на реальном шлюзе |
| Шлюз, который сам проверяет доменный пароль | RADIUS, `first_factor=gateway` («Сам шлюз») | да (только PAP) | в режиме «только логин»: Reply-Message показывается пользователю | на реальном шлюзе не проверено |
| Cisco ASA / Secure Client | RADIUS | да | да (по документации) | требует проверки на реальном шлюзе |
| FortiGate | RADIUS, `remoteauthtimeout 60` | да | да (по документации) | требует проверки на реальном шлюзе |
| MikroTik RouterOS | RADIUS | да | по имеющимся сведениям нет; таймаут ≤ ~10 с | надёжного сценария нет |
| pfSense (OpenVPN) | RADIUS | да | нет | требует проверки на реальном шлюзе |

Конфигурации и шаги: [Подключение VPN](../wiki/Подключение-VPN.md). Адрес RADIUS-клиента в MFA Gate — адрес, с которого пакеты приходят на сервер (после NAT); для NPS — адрес сервера NPS. Доступ к UDP 1812 ограничивается в цепочке `DOCKER-USER` ([install.md](install.md#межсетевой-экран)).

## Шлюзы, которые сами проверяют доменный пароль

Такой шлюз сам проверяет логин и пароль сотрудника, а у внешнего RADIUS-сервера спрашивает только второй фактор. Поддерживается только PAP.

**MFA Gate.** RADIUS-клиент: адрес шлюза (после NAT), ресурс VPN, **Кто проверяет доменный пароль** — **Сам шлюз**, секрет — сгенерированный.

**Шлюз.** Внешний RADIUS-сервер второго фактора:

| Параметр шлюза | Значение | Почему |
|---|---|---|
| Адрес сервера | адрес сервера MFA Gate | — |
| Секрет | секрет RADIUS-клиента | — |
| Порт | `1812` (или ваш `MFA_GATE_RADIUS_PORT`) | — |
| Время ожидания | не меньше `60` с | больше `MFA_GATE_PUSH_TIMEOUT` (45 с); при значении по умолчанию в несколько секунд push не успевает |
| Число попыток | 1–3 | повторы распознаются, второго push нет |
| Режим запроса | «только логин» — push и TOTP; «логин и одноразовый код» — только TOTP | см. ниже |

Режимы:

- **Только логин** — шлюз проверил логин и пароль и шлёт логин с пустым паролем. MFA Gate отправляет push и держит запрос до решения; если push недоступен, а TOTP есть — Access-Challenge, шлюз показывает Reply-Message «Введите одноразовый код» и отправляет код.
- **Логин и одноразовый код** — шлюз сам спрашивает код и шлёт логин и код; MFA Gate проверяет его как TOTP. Push в этом режиме не используется.

При подключении проверьте: доходит ли Message-Authenticator (нет `radius.bad_authenticator` в аудите), передаётся ли Calling-Station-Id, какой Reply-Message видит пользователь и читается ли кириллица. Пошагово: [Шлюзы с собственной проверкой пароля](../wiki/Шлюзы-с-собственной-проверкой-пароля.md).

## Скрипт OpenVPN без RADIUS

`integrations/openvpn/mfa-gate-openvpn.sh` — обработчик `auth-user-pass-verify … via-file` с отложенной проверкой: возвращает OpenVPN код 2 и записывает решение в `auth_control_file`, когда придёт ответ. Настройки — в `/etc/openvpn/mfa-gate.conf` (`MFA_GATE_OPENVPN_CONF` — другой путь):

| Переменная | Назначение |
|---|---|
| `MFA_GATE_URL` | адрес MFA Gate (`https://mfa.example.org`) |
| `MFA_GATE_KEY` | ключ API `key_id:секрет` с правом `auth:write`, привязанный к ресурсу VPN |
| `MFA_GATE_WAIT` | сколько ждать решения, секунд (по умолчанию 50) |

- `static-challenge` в конфигурации клиента: ответ `SCRV1:<пароль>:<код>` разбирается, код передаётся в поле `otp`. Пустой код — подтверждение на телефоне.
- В `source_ip` уходит `untrusted_ip`, в `client_name` — `OpenVPN <common_name>`.
- Ключ и пароль не попадают в аргументы процессов: ключ передаётся `curl` через дескриптор файла, пароль — в теле запроса.
- Любая ошибка (сеть, HTTP-ошибка, таймаут) — отказ. Решения пишутся в syslog с тегом `mfa-gate-openvpn`.
- Скрипт работает через REST API, поле «Первый фактор» RADIUS-клиента к нему не относится: пароль проверяет MFA Gate (поле `password` в запросе).
- `MFA_GATE_URL` — внутренний адрес (`MFA_GATE_PUBLIC_URL`): REST API на внешнем имени Device API не публикуется.
- Если OpenVPN понижает права (`user`/`group` в `server.conf`), файл настроек должен быть читаем этой группой (`640`, группа OpenVPN).

## REST API для своих приложений

Если приложение само принимает логин и пароль, оно может спросить MFA Gate через REST API. Протокол RADIUS для этого не нужен.

1. В панели создайте ключ API с правом `auth:write`. Если нужно, привяжите ключ к ресурсу и ограничьте адресами. Секрет показывается один раз.
2. Сохраните ключ в файле с правами 600. Не передавайте его в аргументах командной строки: аргументы видны другим пользователям в списке процессов.

```bash
# /etc/mfa-gate/api.curl (права 600): параметры curl, ключ в формате key_id:secret
user = "tf_XXXXXXXXXXXX:СЕКРЕТ"
```

Запрос входа:

```bash
curl -fsS -K /etc/mfa-gate/api.curl -H 'Content-Type: application/json' \
  -d @- https://mfa.example.org/api/v1/access-requests <<'EOF'
{"login": "ivanov", "password": "<пароль>", "source_ip": "203.0.113.10", "client_name": "Портал"}
EOF
```

Ответ:

```json
{"id": "6f1c…", "status": "pending", "reason": null, "message": "", "method": "push", "expires_at": "2026-11-18T21:01:00+00:00"}
```

| `status` | Что делать |
|---|---|
| `accepted` | пустить |
| `rejected` | отказать; `reason` — код причины ([admin-guide.md](admin-guide.md#история-входов)) |
| `pending` | ждать решения на телефоне: `GET /api/v1/access-requests/{id}?wait=30` (long-poll до 30 с, повторять до `expires_at`) |
| `challenge` | спросить у пользователя код и отправить `POST /api/v1/access-requests/{id}/otp` с `{"code": "123456"}` |

```bash
curl -fsS -K /etc/mfa-gate/api.curl "https://mfa.example.org/api/v1/access-requests/$ID?wait=30"
```

- Поле `password` не передаётся, если пароль уже проверило само приложение. Тогда MFA Gate проверяет только второй фактор; запись и группы доменного пользователя берутся из каталога, как в режиме `gateway`.
- Код можно передать сразу в поле `otp` первого запроса.
- Если ключ привязан к ресурсу, `resource_id` в запросе должен с ним совпадать, иначе — 403 `resource_mismatch`.
- Если на ожидании `pending` время вышло, повторный `GET` вернёт `rejected` с причиной `push_expired` (после того как фоновый процесс отметит истечение, обычно до 10 с).

Подробности: [api.md](api.md), OpenAPI: `https://mfa.example.org/api/docs`.

## Что проверить на реальном шлюзе

- [ ] Пакеты доходят: в RADIUS-клиенте MFA Gate обновляется «последний запрос», в журнале `radius` нет «неизвестного клиента».
- [ ] Шлюз отправляет Message-Authenticator (нет `radius.bad_authenticator` в аудите).
- [ ] Пароль приходит по PAP (нет ответа «Поддерживается только PAP»).
- [ ] Неверный пароль: отказ приходит сразу, причина `ldap_password` или `local_password`.
- [ ] Push: подтверждение за 30–40 с — VPN подключается. Шлюз не обрывает ожидание раньше.
- [ ] Push: «Отклонить» — отказ приходит сразу, причина `push_denied`.
- [ ] Нет ответа: отказ по истечении `MFA_GATE_PUSH_TIMEOUT`, а не таймаут шлюза.
- [ ] Повторы шлюза не дают второго уведомления на телефон.
- [ ] В запросе на телефоне виден правильный IP клиента (`Calling-Station-Id`).
- [ ] Access-Challenge: клиент показывает запрос кода, кириллица читается, код принимается, повтор кода отклоняется.
- [ ] Переподключение и повторная аутентификация (renegotiation) не запрашивают push слишком часто.
- [ ] Шлюз не требует Accounting для успешного входа.
- [ ] Режим `gateway`: пустой пароль даёт push, код из 6–8 цифр принимается как TOTP, неверный пароль на шлюзе не доходит до MFA Gate.
- [ ] Телефон в мобильной сети (без VPN и Wi-Fi офиса) получает и подтверждает запрос через внешний адрес Device API.
