# Каталог LDAP / Active Directory

Модуль `server/mfa_gate/services/ldap.py` проверяет первый фактор (пароль) в каталоге, читает профиль и группы пользователя и выполняет пошаговую диагностику подключения. Настройки каталога хранятся в таблице `ldap_directories` (модель `LdapDirectory`).

## Интерфейс

```python
from mfa_gate.services import ldap

user = await ldap.authenticate(directory, login, password)   # DirectoryUser или LdapError
user = await ldap.lookup(directory, login)                   # DirectoryUser | None, без пароля
steps = await ldap.diagnose(directory, login=None, password=None)
```

`DirectoryUser`: `dn`, `external_id`, `login`, `display_name`, `email`, `phone`, `groups`. В `groups` для каждой группы лежат и DN, и CN, поэтому политика может ссылаться на группу любым из двух имён. Сравнение выполняйте без учёта регистра (см. `ldap.group_allowed`).

`LdapError.code`:

| Код | Когда |
|---|---|
| `invalid_credentials` | неверный пароль; пустой пароль (отклоняется без обращения к серверу) |
| `account_disabled` | учётная запись отключена (`userAccountControl`, AD 533/701) или вход ограничен (AD 52f/530/531) |
| `account_locked` | AD 775 |
| `password_expired` | AD 532 |
| `must_change_password` | AD 773 |
| `not_found` | пользователь не найден, логин недопустим, под логин подходит несколько записей |
| `not_allowed_group` | пользователь не входит ни в одну из `allowed_groups` |
| `unavailable` | ни один контроллер не ответил (DNS, TCP, тайм-аут) |
| `tls_error` | сертификат не прошёл проверку, имя узла не совпало, STARTTLS отклонён, сервер требует шифрования |
| `config_error` | неполная настройка, сервисная учётная запись не вошла, не найден base DN, нет атрибута-идентификатора |

В `LdapError.detail` пишется причина для журнала администратора: код LDAP и подкод AD (`LDAP 49 invalidCredentials; AD 775: учётная запись заблокирована`). Пароли не попадают ни в `detail`, ни в шаги диагностики, ни в журнал.

## Порядок входа

1. Пустой пароль сразу даёт `invalid_credentials`, потому что пустой пароль означает анонимный bind.
2. Логин разбирается: принимаются `user`, `DOMAIN\user` и `user@domain`. Поиск идёт по `login_attribute` (имя без домена или полное значение), а в AD ещё и по `userPrincipalName`. Значения экранируются (RFC 4515).
3. Если задан `bind_dn`, выполняется bind сервисной записью. Если её не пустили, это `config_error`, а не «неверный пароль» пользователя. Поиск идёт под `base_dn` с фильтром `(&<user_filter><условие логина>)`.
4. В AD отключённая запись (`userAccountControl & 2`) отклоняется до проверки пароля, чтобы не увеличивать счётчик неудачных попыток в AD. В счётчик блокировки MFA Gate идёт только неверный пароль.
5. Пароль проверяется через bind найденного DN паролем пользователя.
6. Затем читаются группы и проверяется `allowed_groups`. Пустой список означает, что вход разрешён всем найденным.

**Без сервисной учётной записи** (`bind_dn` пуст) пользователь входит сам, после чего его собственными правами читаются его запись и группы:
- в AD bind выполняется по UPN или `DOMAIN\user` в том виде, как их ввели. Короткое имя дополняется доменом из `DC=` компонентов `base_dn` (`alice` превращается в `alice@corp.example`);
- в OpenLDAP DN собирается как `<login_attribute>=<имя>,<base_dn>`, поэтому `base_dn` должен указывать на OU пользователей. Группы ищутся под тем же `base_dn`. Если группы лежат в другой OU, нужна сервисная запись.
- `lookup` без сервисной записи невозможен и возвращает `config_error`.

## Группы

- **AD, `nested_groups=true`.** Используется один постраничный поиск `(&(objectClass=group)(member:1.2.840.113556.1.4.1941:=<DN>))` (LDAP_MATCHING_RULE_IN_CHAIN). Если правило не поддерживается, берутся прямые группы из `memberOf`, а в журнал пишется предупреждение.
- **AD без вложенности:** только `memberOf`.
- **OpenLDAP:** группы ищутся по `member`/`uniqueMember` (классы `groupOfNames`, `groupOfUniqueNames`, `group`) сначала для пользователя, потом для найденных групп. Глубина не больше 10 уровней, каждая группа посещается один раз, так что циклы безопасны. Overlay `memberOf` не требуется, но его значения тоже учитываются. Если поиск групп завершился ошибкой, вход отклоняется: неполный список групп мог бы обойти запрещающую политику (`exclude_groups`).

## Идентификатор

`id_attribute=objectGUID` переводится из 16 байт в строку UUID (`uuid.UUID(bytes_le=…)`), то есть в тот вид, в котором его показывает AD. Остальные атрибуты (`entryUUID`, `uid` …) берутся как есть. Запись без идентификатора даёт `config_error`, потому что без устойчивого ключа пользователя нельзя сопоставить с его устройствами.

## Контроллеры, TLS, тайм-ауты

- `hosts` — список контроллеров, порт у всех общий (`port`). Используется `ServerPool(FIRST, active=1, exhaust=60)`: первый доступный контроллер, а не ответивший исключается на 60 с. Пул хранится отдельно для каждого каталога и пересоздаётся при изменении настроек. Если исключены все контроллеры, их снова проверяют, а не отказывают без попытки.
  - Значение `active=True` из документации ldap3 не используется: при отказе всех узлов ldap3 перебирает их бесконечно, и вход завис бы.
- `connect_timeout` и `receive_timeout` равны `timeout` (от 1 до 60 с). Недоступный контроллер стоит не больше `timeout` секунд на попытку.
- `encryption`: `ldaps` (обычно 636), `starttls` (389) или `none`. При `none` пароли идут открытым текстом, применять только в изолированной сети.
- `verify_tls=true` (по умолчанию) включает `CERT_REQUIRED` и сверку имени узла. Доверенные CA берутся из `ca_cert` (PEM, можно несколько), а если поле пусто — из системного набора. Некорректный PEM даёт `config_error`.
- **Имя узла.** Подключайтесь к контроллерам по DNS-имени из сертификата. ldap3 на Python 3.12+ сверяет имя своей функцией, а она не принимает IP-адрес как имя. Поэтому подключение по IP при `verify_tls=true` закончится `tls_error`, даже если IP есть в SAN.
- Переходы по ссылкам (referrals) выключены. Соединения работают только на чтение.
- ldap3 блокирующий, поэтому каждая операция целиком выполняется в `asyncio.to_thread`. Поля `LdapDirectory` считываются заранее, в потоке событийного цикла, и пароль сервисной записи расшифровывается там же (`box().decrypt(…, aad=b"ldap:" + id)`).

## Диагностика

`diagnose()` возвращает список шагов `{"step", "ok", "detail", "ms", "host"}`.

- `dns`, `tcp`, `tls` выполняются для **каждого** хоста. Хост, не прошедший шаг, дальше не проверяется. Если не прошёл ни один хост, диагностика заканчивается.
- Затем `bind` (сервисная запись, а без неё bind пользователем по переданным логину и паролю), `base_dn` (чтение BASE), `user_search` (если передан логин), `user_bind` (если передан пароль), `groups` (с вложенностью). Шаг `groups` получает `ok=false`, если ни одна группа не входит в `allowed_groups`.
- Остановка происходит на первом неуспешном шаге после сетевых. В `detail` нет паролей. Неполная настройка (нет hosts или base_dn, нет пароля сервисной записи) вызывает `LdapError(config_error)` до сетевых шагов.

## Пример настройки

| Поле | Active Directory | OpenLDAP |
|---|---|---|
| hosts | `["dc1.corp.example", "dc2.corp.example"]` | `["ldap.example.org"]` |
| port / encryption | 636 / ldaps | 636 / ldaps или 389 / starttls |
| bind_dn | `CN=svc-mfa-gate,OU=Service,DC=corp,DC=example` | `cn=readonly,dc=example,dc=org` |
| base_dn | `DC=corp,DC=example` | `dc=example,dc=org` |
| user_filter | `(&(objectClass=user)(objectCategory=person))` | `(objectClass=inetOrgPerson)` |
| login_attribute / id_attribute | `sAMAccountName` / `objectGUID` | `uid` / `entryUUID` |
| allowed_groups | `["VPN Users"]` или DN группы | `["vpn-users"]` |

Сервисной записи достаточно прав на чтение пользователей и групп. Запись в каталог не нужна.

## Тесты

- `pytest tests/test_ldap.py` запускает юнит-тесты без сервера: подкоды AD, разбор логина, objectGUID, экранирование фильтра, проверку настроек, обход групп (глубина и циклы), откат AD к `memberOf`, отказ на пустом пароле без обращения к сети. Тесты с меткой `ldap` пропускаются.
- `tests/ldap_fixture/run.sh` поднимает OpenLDAP (`osixia/openldap:1.5.0`) в Docker с портами только на 127.0.0.1 и одноразовым CA и сертификатом сервера, засевает `ou=people`/`ou=groups` с вложенностью `vpn-users ⊃ engineers ⊃ alice` и циклом `loop-a ⇄ loop-b`, выполняет `pytest -m ldap`, а потом удаляет контейнер и временные файлы. Пароли случайные на каждый прогон.
- Не покрыто: настоящий Active Directory (LDAP_MATCHING_RULE_IN_CHAIN, подкоды 52e/775/…, `userAccountControl`, bind по UPN). Эта логика проверена юнит-тестами на записанных ответах, но не на живом контроллере.
